# ADR-0007: 모의투자 주문 계획과 위험검사 경계

- 상태: 승인
- 결정일: 2026-08-18
- 승인: 사용자가 2026-08-18에 네 가지 결정을 승인 — ① 첫 구현 단계는 증권사 주문 제출 전까지(계좌 조회·목표 포지션·위험검사·주문 계획·상태 머신), ② 목표 비중은 승인된 정책 한도를 상한으로 사용, ③ 주문 상태는 현재 상태 1행 + append-only 이벤트 로그, ④ 계좌번호는 secret 파일로 배선하고 실계좌 검증은 파일 제공 후 수행
- 관련 결정: [ADR-0004 AI 신호와 주문 실행 분리](0004-ai-execution-separation.md)
- 관련 정책: [거래 안전 정책](../spec/trading-safety-policy.md), [모의투자·실전투자 전환 게이트](../spec/paper-to-live-gate.md)
- 관련 계약: [주문 계획·위험검사 데이터 계약](../data/order-planning-risk-contract.md)

## 배경

6단계까지는 데이터 수집과 백테스트만 존재했고 증권사 쓰기 경로가 없었다. 7단계는 전략 신호를
실제 주문으로 바꾸는 단계이며, 손실로 직결되는 첫 코드다. [거래 안전 정책](../spec/trading-safety-policy.md)의
한도와 주문 가능 조건은 문서로만 존재했고 실행 가능한 코드로 표현되지 않았다.

동시에 두 가지 구조적 제약이 있다. 첫째, ADR-0004는 `전략 신호 → 목표 포지션 → 결정적
위험검사 → 주문 계획 → 증권사 API` 순서를 요구한다. 둘째, 정책 §4는 주문 판단에 사용하는
현재가가 수신 후 10초 이내여야 하는데 기존 시세는 배치 수집이라 이 조건을 만족할 수 없다.

## 결정

### 1. 주문 계획과 주문 제출을 분리한다

이 단계는 `PLANNED` 상태의 주문까지만 만들고 증권사 쓰기 API를 호출하지 않는다. 주문 제출·정정·
취소·체결 동기화는 다음 단계이며, 그때도 이 문서의 위험검사를 통과한 계획만 입력으로 받는다.
위험검사 엔진이 주문 제출 코드보다 먼저 존재해야 우회 경로가 생기지 않는다.

### 2. 위험검사는 순수 결정적 함수이며 모든 판정을 보존한다

위험검사는 외부 호출이 없는 순수 함수로 구현하고, 같은 입력에 항상 같은 판정을 낸다. 주문마다
적용된 모든 규칙의 한도값·예상값·통과 여부를 저장한다. 전략, AI, 화면, worker는 이 엔진을
우회하는 경로를 갖지 않는다. 한도는 정책 §3의 값을 코드 상수로 표현하며 코드에서 완화할 수 없다.

### 3. 목표 비중은 승인된 정책 한도를 상한으로 사용한다

매수 신호는 종목 한도(NAV 10%)를 목표 비중으로, 매도 신호는 0%를 목표로 한다. 주문 1건 한도
(NAV 5%)를 넘는 필요 수량은 여러 주문으로 분할한다. 백테스트의 가용 현금 전량 매수와 수량·성과가
달라지며, 이 차이는 계약과 검증 문서에 기록한다. 백테스트에 같은 사이징을 적용하는 작업은 후속이다.

### 4. 주문 상태는 현재 상태 1행 + append-only 이벤트 로그다

`trading.order`가 주문당 현재 상태 한 행을 갖고, `trading.order_event`가 상태 전이와 사유를
append-only로 보존한다. 주문 생애주기는 사실의 정정이 아니라 상태 전이이므로 시장 데이터의 버전
사실 패턴을 쓰지 않는다. 중복 주문은 결정적으로 생성한 `client_order_id`의 UNIQUE 제약으로
구조적으로 차단한다. 같은 전략·신호·종목·구분·순번은 항상 같은 식별자를 만들므로 재실행이
새 주문을 만들지 못한다.

### 5. 계좌번호 원문을 저장하지 않고 모의 자격증명만 사용한다

계좌번호와 상품코드는 Docker secret 파일로만 주입하고, 데이터베이스·API 응답·로그·문서에는
해시 참조만 남긴다. 주문 경로에는 모의 자격증명만 주입한다. 실전 키는 승인된 읽기 전용 시장
달력 확인 경로 전용이며 주문·계좌 경로에 주입하지 않는다.

### 6. 기준가는 계획 시점에 새로 조회한 현재가만 사용한다

정책 §4의 10초 규칙을 만족시키기 위해 계획 실행 시점에 KIS 현재가를 새로 조회하고 수신 시각을
기록한다. 배치 수집 시세와 일봉은 주문 판단의 기준가로 사용하지 않는다. 조회에 실패하거나 수신
후 10초를 넘기면 계획을 만들지 않는다. 정책을 완화하지 않고 구현을 정책에 맞춘 결정이다.

### 7. 모든 미확인 상태는 fail-closed다

거래일·세션 미확인, 계좌 조정 미완료, 오래된 기준가, 거래정지 종목, 외부 API 연속 실패,
자동매매 상태가 `RUNNING`이 아닐 때는 주문을 만들지 않고 사유 코드를 기록한다. 조회는 막지 않고
주문 생성만 막는다.

### 8. 자동매매 상태는 재시작·거래일 변경 시 `DISABLED`로 복귀한다

정책 §6의 상태 전이를 그대로 구현한다. 비상정지는 신규 주문을 금지하고 미체결 취소를 시도하되
보유 포지션을 자동 청산하지 않는다. 자동 청산은 이 결정의 범위 밖이며 별도 승인 기능으로만
추가할 수 있다.

## 대안

### 백테스트와 동일한 전량 매수 사이징

승인된 정책의 종목 10%·주문 5%·최소 현금 20% 한도를 위반하므로 채택하지 않는다. 정책을 코드에
맞춰 완화하는 것도 금지한다.

### 주문 제출까지 한 번에 구현

증권사 쓰기 경로가 위험검사와 같은 시점에 들어오면 검증 단위가 커지고, 위험검사가 완성되기 전에
주문 경로가 존재하는 기간이 생긴다. 채택하지 않는다.

### 주문 상태에 버전 사실 패턴 재사용

`version`·`superseded_at`은 같은 사실의 정정을 표현하는 도구다. 주문 상태 전이는 정정이 아니므로
의미가 어긋나고 감사 질의가 복잡해진다. 채택하지 않는다.

## 결과

- 정책의 13개 한도와 주문 가능 조건이 실행 가능한 테스트로 표현된다.
- 증권사에 주문을 보내기 전에 위험검사·감사·상태 머신이 먼저 존재한다.
- 중복 주문이 애플리케이션 로직이 아니라 데이터베이스 제약으로 차단된다.
- 계좌번호가 저장소·API·로그에 존재하지 않는다.
- 업종 분류 데이터가 없는 동안 미분류 합계 한도(NAV 10%)가 전체 노출의 실질 상한이 된다.
  이 보수적 결과는 정책 그대로이며, 완화는 업종 분류 수집과 사용자 결정을 요구한다.

## 재검토 조건

이 결정은 실전매매가 존재하는 동안 유지한다. 주문 제출 단계는 이 문서의 경계를 확장하는 것이
아니라 그 뒤에 붙는다. 한도 완화, 시장가 주문 추가, 자동 청산 추가는 정책 변경이며 문서와
테스트를 먼저 고치고 사람의 승인을 받아야 한다.
