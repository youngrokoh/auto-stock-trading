# ADR-0010: 사람이 확인한 주문 대조 종결

- 상태: 승인
- 결정일: 2026-08-19
- 승인: 사용자가 2026-08-19에 네 가지 결정을 승인 — ① 리스너 부착 전에 제출된 주문만 대상, ② 체결과 취소 둘 다 확정 가능, ③ 수량·평균단가를 사람이 명시 입력, ④ 실행자와 근거를 필수 인자로 받아 기록
- 관련 결정: [ADR-0009 실시간 체결통보 수신 경계](0009-realtime-fill-notification.md), [ADR-0008 모의투자 주문 제출·체결 동기화 경계](0008-paper-order-submission.md), [ADR-0007 모의투자 주문 계획과 위험검사 경계](0007-paper-order-planning-and-risk.md)
- 관련 정책: [거래 안전 정책](../spec/trading-safety-policy.md), [모의투자·실전투자 전환 게이트](../spec/paper-to-live-gate.md)
- 관련 계약: [주문 제출·체결 동기화 계약](../data/order-submission-contract.md), [실시간 체결통보 계약](../data/realtime-fill-notification-contract.md)

## 배경

2026-08-19 마감 후 확인에서 일별주문체결조회(`VTTC8001R`)가 **모의환경에서는 시각·파라미터와
무관하게 주문별 행(`output1`)을 주지 않는다**는 사실이 확정됐다(장중 6·마감 후 3, 총 9가지 조합).
같은 응답의 `output2` 집계는 그날 체결을 정확히 반영한다.

그 결과 두 가지가 남았다.

- ADR-0009 결정 1의 후반부("마감 후 이 조회로 재대조")를 모의환경에서 수행할 수 없다.
- 2026-08-19 오전에 제출한 주문 2건(`0000008637`, `0000008645`, 각 2주)은 실제로 전량 체결됐지만
  내부에서 `SUBMITTED`로 남았다. 체결통보는 리스너가 붙은 뒤 발생한 체결만 주므로 소급 확정할 수
  없고, 미체결이 남아 있으므로 계획이 계속 `ACCOUNT_NOT_RECONCILED`로 차단된다.

즉 증권사 응답만으로는 영구히 풀 수 없는 상태가 만들어졌다. 이 결정은 그 상태를 **사람이 확인한
사실**로 종결하는 좁은 예외 경로를 정의한다. 사람의 확인이 증권사 응답을 대신하므로, 남용될 수 없도록
범위·입력·기록을 코드보다 먼저 고정한다.

## 결정

### 1. 리스너 부착 전에 제출된 주문만 대상으로 한다

대상 주문의 제출 시각이 그 환경의 **가장 이른 체결통보 세션 시작 시각보다 이전**이어야 한다.
체결통보로 확정될 수 있었던 주문은 사람이 손댈 수 없다. 이 규칙은 시간이 흐를수록 대상 집합이
늘어나지 않고 닫히므로, 정상 확정 경로를 사람이 우회하는 일이 구조적으로 불가능하다.

세션 기록이 아예 없는 환경(리스너를 한 번도 띄우지 않은 환경)에서는 이 경로를 쓸 수 없다. 먼저
리스너를 붙여 정상 경로를 갖춘 뒤에만 과거를 정리한다.

### 2. 체결과 취소를 모두 확정할 수 있다

허용 목표 상태는 `FILLED`·`PARTIALLY_FILLED`·`CANCELED`다. 증권사에서 취소된 주문도 확정할 수
없으면 같은 방식으로 영구히 막히므로 함께 넣는다. `REJECTED`는 제출 응답으로 이미 기록되므로
제외한다. 상태 그래프(`domain/orders/models.py`)가 막는 전이는 이 경로도 할 수 없다.

### 3. 수량과 평균단가는 사람이 명시 입력하고 값을 만들지 않는다

체결 수량과 평균 체결가는 사람이 KIS 화면에서 읽어 인자로 넣는다. 시스템은 추정하거나 집계에서
역산하지 않는다. 다음을 어기면 거부한다.

- 수량이 주문 수량을 넘음
- 수량이 현재 체결 수량보다 작음(체결 수량은 줄어들 수 없다)
- `FILLED`인데 수량이 주문 수량과 다름
- `PARTIALLY_FILLED`인데 수량이 0이거나 주문 수량과 같음
- 수량이 0보다 큰데 평균단가가 0 이하

### 4. 실행자와 근거를 필수로 받아 감사 기록에 남긴다

`--operator`와 `--evidence`가 없으면 실행되지 않는다. 근거는 사람이 무엇을 보고 확인했는지를 적는
자유 문자열이다(예: "KIS 모의투자 잔고화면 2026-08-19 16:10"). 두 값은 주문 이벤트와 자동매매
이벤트에 함께 남고, 사유 코드는 `HUMAN_ATTESTED`다.

이 전이는 증권사 응답이 근거가 아니므로 감사에서 반드시 구분돼야 한다. `automation_event`에
`attestation` 유형을 추가해 상태 전이·API 실패·대조 불일치·리스너 상태와 별도로 보이게 한다. 값은
자기 주장이며 검증할 수 없다는 점을 계약에 적는다.

### 5. 이 경로는 주문을 보내지 않고 자동매매를 재개하지 않는다

증권사 API를 호출하지 않는다. 주문 상태 한 건과 이벤트만 바꾸며, 자동매매 상태는 건드리지 않는다.
차단이 풀렸는지는 다음 계획 실행이 스스로 판단한다(미체결 없음 + NAV 일치). 실행은 worker CLI
수동 명령으로만 제공하고 HTTP 쓰기 경로를 만들지 않는다(ADR-0007 결정 1, ADR-0008 결정 1 유지).

## 결과

- 증권사 응답으로 풀 수 없는 상태를 사람이 근거를 남기고 종결할 수 있다.
- 대상이 "리스너 부착 전 주문"으로 닫혀 있어 정상 확정 경로를 우회하는 데 쓸 수 없다.
- 감사 로그에서 증권사 사실과 사람의 확인이 구분된다.
- 사람의 입력이 틀리면 내부 상태가 증권사와 달라진다. 그 위험은 근거 기록과 좁은 범위로만 통제되며,
  실전 전환 게이트에서 재검토 항목으로 남는다.

## 대안

- **집계(`output2`) 기반 자동 확정**: 사람 개입이 없어 매끄럽지만, 계좌에 외부(수동) 주문이 섞이면
  합계가 우리 주문만을 뜻하지 않는다. 2026-08-19에 실제로 사용자의 수동 주문이 같은 집계에 포함된
  사례가 관측됐다. 집계로 개별 주문을 나눌 수 없으므로 채택하지 않았다.
- **재대조 포기(웹소켓 단독)**: 구조가 가장 단순하지만 이미 막힌 두 주문을 풀지 못하고, 통보 유실을
  발견할 경로도 없어진다.
- **미체결 차단 규칙 완화**: 계획 차단을 풀면 즉시 진행할 수 있지만, 정책의 계좌 대조 요구를 깎는
  변경이라 검토하지 않았다.
