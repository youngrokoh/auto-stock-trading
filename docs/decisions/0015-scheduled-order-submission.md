# ADR-0015: 자동 스케줄 주문 제출 경계

- 상태: 승인 (2026-08-25 구현)
- 결정일: 2026-08-24
- 승인: 2026-08-24 사용자 승인. 네 가지 답으로 결정 1~3·6·8을 확정했다 — ① 계획-제출 체인으로 한정
  (독립 제출 cron을 만들지 않는다), ② 주기 15분·창 09:05~15:15 KST, ③ 하루 한 번 사람이 켜는 성질
  유지, ④ 차단·실패는 외부 알림으로 노출하고 모의 전용으로 한정
- **구현하지 않았다.** 승인 직후 구현에 들어가 §선행 조건의 의존성을 발견했고, 사용자가 "결정은
  확정하고 구현은 보류"를 선택했다(2026-08-24)
- 관련 결정: [ADR-0008 모의투자 주문 제출·체결 동기화 경계](0008-paper-order-submission.md), [ADR-0007 모의투자 주문 계획과 위험검사 경계](0007-paper-order-planning-and-risk.md), [ADR-0009 실시간 체결통보 수신 경계](0009-realtime-fill-notification.md), [ADR-0006 시장 달력 수집 예약](0006-market-calendar-scheduling.md), [ADR-0005 KIS 토큰·요청 조정](0005-kis-token-and-rate-coordination.md), [ADR-0014 주문·위험 이벤트 외부 알림 경계](0014-outbound-event-notification.md)
- 관련 정책: [거래 안전 정책](../spec/trading-safety-policy.md), [모의투자·실전투자 전환 게이트](../spec/paper-to-live-gate.md)
- 관련 계약: [주문 제출·체결 동기화 계약](../data/order-submission-contract.md), [주문 계획·위험검사 데이터 계약](../data/order-planning-risk-contract.md)

## 배경

ADR-0008 결정 1은 조건부 문장으로 끝난다.

> 첫 슬라이스는 사람이 계획 ID를 지정해 명령을 실행할 때만 증권사에 주문을 보낸다. HTTP 쓰기
> 엔드포인트를 만들지 않고, Taskiq 예약 자동 제출도 만들지 않는다. … **주기적 자동 제출은 이 슬라이스
> 검증 후 별도 승인으로 추가한다.**

그 전제는 충족됐다. 2026-08-19에 실제 모의주문 2건이 접수·체결되고, 그 실행이 드러낸 결함 3건을 고쳤고,
장중 체결 확정 경로(ADR-0009)와 노출 축소 경로(ADR-0013)까지 갖췄다. 이 문서가 그 조건부 문장을
해소한다.

**이것은 경계 변경이다.** ADR-0007 결정 1과 ADR-0008 결정 1이 함께 "제어 표면은 사람의 CLI"를 세웠고,
자동 스케줄 제출은 **사람이 없는 동안 주문이 증권사로 나가는 첫 경로**가 된다.

## 측정한 사실 (2026-08-24, 코드 확인)

초안을 쓰면서 두 가지를 코드에서 확인했다. 둘 다 설계를 바꿨다.

### 1. 주기는 정책 §3의 시도 한도를 소모하지 않는다

`order_attempts_query`는 당일 **`trading.order` 행 수**를 센다(`trading_queries.py`). 스케줄러 틱이나
제출 호출이 아니라 **주문이 몇 개 만들어졌는가**다. 따라서 보낼 것이 없는 틱은 0건을 쓰고, 하루 20건
한도는 **계획 경로**를 묶는다.

초안 검토 중 "5분 주기면 장중 74회 실행이라 시도 한도에 걸린다"고 적었던 것은 틀렸다. 주기 선택의
제약은 시도 한도가 아니라 KIS 요청 슬롯(ADR-0005)이다.

### 2. 10초 기준가 규칙은 제출 시점에 검사되지 않는다 — 이것이 핵심 위험이다

정책 §4의 "주문 판단에 사용하는 현재가가 수신 후 10초 이내"는 `domain/risk/engine.py`(계획 시점)와
`application/trading/revision.py`(정정 시점)에서만 강제된다. **제출 경로(`submission.py`의 `_block_code`)는
자동매매 상태·거래일·주문 허용시간·리스너 부착만 본다.** 기준가 나이는 보지 않는다.

제출 대상은 `pending_orders(environment, trading_date, plan_id)`로 **거래일 단위**로만 걸러진다. 즉
09:10에 계획한 주문이 같은 날 15:10에 제출될 수 있고, 그 지정가는 6시간 전 기준가에 근거한다.

지금은 위험하지 않다 — 사람이 `--plan` 직후 `--submit`을 실행하므로 간격이 초 단위다. **자동화하면서
계획과 제출을 분리하는 순간 이 간격이 실제 위험이 된다.**

## 선행 조건: 실시간 신호 원천이 없다

**승인 후 구현에 들어가 발견했다.** 결정 1은 예약 작업이 계획을 만든다고 전제하지만, 계획 경로에는
무엇을 사고 팔지 정하는 **신호 원천이 없다.**

코드에서 확인한 사실(2026-08-24):

- `SignalCandidate`를 만드는 곳은 두 군데뿐이다. `worker/execution/planning.py`(사람이 `--symbol`·
  `--side`로 지정)와 `application/trading/revision.py`(기존 주문에서 그대로 가져온다).
- `OrderPlanner`는 후보를 **입력으로 받고** 지표를 계산하지 않는다. `candidates`는 요청 필드다.
- 요청의 전략 이름·버전·파라미터는 **계보 기록용**이다. 신호를 만들지 않는다.
- 2026-08-19 실주문도 사람이 종목과 방향을 지정해 나갔다.

즉 예약 작업이 "계획"을 하려면 후보를 정하는 원천이 필요하고, 그것을 임의로 만들 수 없다. 손실에 직결되는
판단이며 [ADR-0004 AI 신호와 주문 실행 분리](0004-ai-execution-separation.md)가 세운 경계에 닿는다.
백테스트 전략(v1~v4)과 8단계 ML 모델은 있지만 실주문 경로에 연결돼 있지 않다.

**따라서 이 ADR의 결정은 유효하지만 구현은 신호 원천이 생긴 뒤다.** 신호 원천 자체는 별도 ADR과 승인
사항이다 — "저장된 전략 신호를 실계좌 주문 후보로 잇는다"는 이 문서보다 큰 결정이다.

**해소됨(2026-08-25).** [ADR-0016 실주문 신호 원천 경계](0016-live-signal-source.md)가 승인·구현됐다.
신호는 `strategy.live_signal`에 저장되고 `planning.py --from-signal`이 보유와의 차집합으로 후보를
만든다. 이 ADR의 구현(계획-제출 체인의 예약화)은 이제 막힌 것이 없다.

검토한 대안(채택하지 않음): 설정에 종목·방향을 고정해 두고 예약을 돌리는 방식. 구현은 가장 빠르지만
전략이 아니라 반복 주문이며, 시장 상황과 무관하게 같은 방향으로 주문이 계속 나간다.

### 구현 시 함께 필요한 것 (기록)

결정 6을 지키려면 차단 사실이 **저장돼야** 한다. 지금 제출 게이트는 `LISTENER_NOT_ATTACHED` 같은 차단
코드를 반환만 하고 기록하지 않으며, CLI 출력으로만 드러난다 — 자동 실행에서는 그 출력을 보는 사람이 없다.
`trading.automation_event`에 `schedule_blocked` 유형을 더하는 마이그레이션과 ADR-0014 선별 규칙 갱신이
구현 슬라이스에 포함된다. 생산자 없는 이벤트 유형을 미리 만들지 않기 위해 이번에는 넣지 않았다.

## 결정

### 1. 자동 제출은 계획과 한 작업으로 묶는다 — 독립 제출 cron을 만들지 않는다

예약 작업은 `계획 → (성공 시 곧바로) 제출`을 한 실행 안에서 수행한다. 이미 저장된 `PLANNED` 주문을
주기적으로 훑어 보내는 독립 제출기는 만들지 않는다.

근거는 위 측정 2다. 계획이 방금 만든 주문만 제출하면 기준가 나이가 초 단위로 유지되고, 정책 §4가 계획
시점에 강제한 10초 규칙이 제출에도 실질적으로 유효하다. 독립 제출기를 두면 그 규칙을 제출 경로에
새로 구현해야 하고(기준가 재조회 또는 계획 나이 상한), 규칙이 두 곳으로 갈라진다.

**부수 효과로 범위 문제도 사라진다.** 자동 제출이 과거 계획의 잔여 `PLANNED` 주문을 집어갈 경로가
없어진다 — 그 주문들은 사람이 `--submit --plan-id`로만 보낼 수 있다.

### 2. 트리거는 서울 기준 cron이며 주문 허용시간 안에서만 돈다

ADR-0006의 패턴을 그대로 쓴다: 하나의 Taskiq scheduler, 서울 시간 cron, PostgreSQL 실행 claim으로
중복 방지. 기본 주기는 **15분**이고 창은 **09:05~15:15 KST**다.

주기 값의 제약은 시도 한도가 아니라(측정 1) KIS 요청 슬롯이다. 한 실행은 계획(종목별 시세 조회)과
제출을 합쳐 수십 회의 KIS 호출을 쓰며, 모의환경은 초당 1건으로 직렬화된다(ADR-0005). 15분은 한
실행이 끝나기 전에 다음 실행이 겹치지 않는 여유를 준다.

### 3. 하루 한 번은 사람이 켠다

정책 §6이 거래일 변경 시 자동매매를 `DISABLED`로 되돌린다. 따라서 자동 제출도 **사람이 그날
`running`으로 올린 뒤에만** 동작한다. 예약 작업이 자동매매 상태를 올리는 경로는 만들지 않는다.

이 성질이 자동화의 상한이다. 사람이 아무것도 하지 않는 날에는 주문이 나가지 않는다.

### 4. 예약은 scheduler, 실행은 worker — scheduler는 주문 자격증명을 갖지 않는다

ADR-0006 결정의 규칙을 유지한다. scheduler는 작업 메시지만 발행하고, KIS 주문 키와 계좌 비밀은 실행
worker에만 secret 파일로 준다. 기본 Compose에는 이 worker가 없고 opt-in 오버라이드로만 켠다.

### 5. 중복 방지는 두 겹이다

`operations.scheduled_job_run` 실행 claim이 같은 슬롯의 중복 실행을 막고(ADR-0006), `client_order_id`
UNIQUE가 같은 신호의 중복 주문을 막는다(ADR-0007). 앞의 것이 실패해도 뒤의 것이 증권사 주문을 두 번
만들지 않는다.

### 6. 차단과 실패는 조용히 지나가지 않는다

자동 경로에서는 사람이 화면을 보고 있지 않으므로 **조용한 실패가 가장 위험하다.** 리스너 미부착
(`LISTENER_NOT_ATTACHED`), 계좌 미조정(`ACCOUNT_NOT_RECONCILED`), 위험 거절, API 연속 실패는 ADR-0014의
외부 알림 경로로 내보낸다. 이미 그 이벤트들은 저장되고 선별 대상이므로 새 경로를 만들지 않는다.

"아무 주문도 나가지 않은 것"과 "차단돼서 나가지 않은 것"이 구분돼야 한다.

### 7. 정지는 상태 전이로 즉시 듣는다

`PAUSED`·`EMERGENCY_STOP`으로 전이하면 다음 실행이 차단된다(제출 게이트가 이미 상태를 본다). 스케줄
자체를 끄는 것은 Compose 오버라이드를 내리는 것이며, 그 사이 실행 중인 작업은 상태 전이로 멈춘다.

### 8. 모의 전용이다

실전 환경에서는 이 경로를 활성화하지 않는다. 실전 자동 제출은 전환 게이트를 통과한 뒤 **별도 승인**
사항이다(정책과 게이트 문서의 기존 규칙 유지).

## 결과

승인되면:

- 신호 발생과 제출 사이 지연이 사람의 실행 시점에 의존하지 않는다(계약 §한계에 기록된 항목 해소).
- 사람의 개입은 하루 한 번(자동매매 켜기)으로 줄어든다.
- 사람이 없는 동안 주문이 나간다. 이것이 이 결정의 실질적 비용이며, 결정 3·6·7이 그 비용을 제한한다.

승인되지 않으면:

- 제출은 계속 사람의 CLI 실행이다. 지금까지 이것이 손실로 이어진 관측은 없다 — 모의 실주문은 사람이
  실행한 시점에 접수됐고 즉시 체결되거나 의도적으로 미체결로 남았다.

## 대안

- **독립 제출 cron**: 계획과 제출을 분리해 각각 주기를 준다. 구현이 단순해 보이지만 10초 기준가 규칙을
  제출 경로에 새로 구현해야 하고(측정 2), 과거 계획의 잔여 주문을 집어갈 범위 문제가 생긴다.
- **계획 나이 상한을 두고 독립 제출 유지**: 예를 들어 계획 후 60초 이내만 자동 제출한다. 규칙이 하나
  늘고, 상한을 넘긴 주문이 "사람이 보내야 하는 주문"으로 남아 운영이 복잡해진다.
- **제출 시점에 기준가 재조회**: 가장 엄격하지만 제출마다 시세 조회가 추가돼 요청 슬롯을 두 배로 쓰고,
  재조회 값이 지정가 밴드를 벗어나면 제출을 거절해야 한다 — 사실상 정정 경로(ADR-0011)의 재구현이다.
- **HTTP 쓰기 엔드포인트로 화면에서 제출**: 사람이 화면에서 누른다는 점은 유지된다. 그러나 ADR-0007
  결정 1이 세운 "제어 표면은 CLI" 경계를 바꾸는 별개의 결정이며, 자동화 문제를 해결하지 않는다.

## 재검토 조건

- **신호 원천이 승인되면 이 문서의 결정으로 구현에 들어간다**(§선행 조건). 결정 자체는 다시 논의하지
  않는다.
- 제출 경로에 기준가 나이 검사가 추가되면 결정 1의 근거가 약해진다. 그때 독립 제출기를 다시 검토한다.
- 한 실행이 15분을 넘기는 것이 관측되면 주기를 다시 정한다.
- 실전 전환 게이트를 통과하면 결정 8을 다시 검토한다.

## 구현 (2026-08-25)

| 결정 | 구현 |
|---|---|
| 1. 계획-제출 체인 | `ScheduledSubmissionOperation`이 한 실행에서 계획 후 그 `plan_id`만 제출한다. 독립 제출 cron 없음 |
| 2. 15분 주기·창 | `submission_schedules()`가 09:05~15:05 KST 25슬롯(평일)을 만든다. 창 밖 슬롯은 만들지 않는다 |
| 3. 하루 한 번 사람이 켠다 | 예약 경로에 상태 전이가 없다. 꺼져 있으면 `AUTOMATION_NOT_RUNNING`으로 차단된다 |
| 4. scheduler/worker 분리 | `infra/compose.order-submission-schedule.yaml` — scheduler는 주문 secret을 받지 않는다 |
| 5. 중복 방지 두 겹 | 슬롯 단위 실행 claim(`order-submission:YYYY-MM-DDTHH:MM`) + `client_order_id` UNIQUE |
| 6. 차단은 사실로 | `trading.automation_event`의 `schedule_blocked`(리비전 `20260825_0030`), ADR-0014 선별에서 경고로 취급 |
| 7. 정지는 상태 전이로 | 제출 게이트가 이미 상태를 본다. 예약은 그 게이트를 우회하지 않는다 |
| 8. 모의 전용 | 계획·제출 진입점의 `KisEnvironment.PAPER` 확인을 그대로 탄다 |

후보는 [ADR-0016](0016-live-signal-source.md)의 저장된 신호에서 나온다. 예약 실행은 신호를 계산하지
않는다.

### 구현 중 드러난 위험 하나

`ScheduledJobExecutor.execute`는 `operation.run()`을 **try 없이** 호출한다. 예외가 새어 나가면 claim이
결과 없이 남아 lease 만료(9분)까지 감사 기록이 빈다. 주문 경로에서는 그 공백을 허용하지 않으므로 실행이
모든 예외를 붙잡아 실패 사유로 바꾼다. 테스트가 이 성질을 고정한다.

`no_plan`(신호 없음·후보 없음)은 **차단이 아니다.** 차단 이벤트를 만들지 않는다 — 할 일이 없는 것과
막힌 것이 같은 신호가 되면 알림이 의미를 잃는다.
