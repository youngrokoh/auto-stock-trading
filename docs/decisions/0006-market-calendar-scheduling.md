# ADR-0006: 시장 달력 스케줄 실행과 중복 방지

- 상태: 승인
- 제안일: 2026-08-16
- 승인일: 2026-08-16
- 관련 결정: [ADR-0001](0001-modular-monolith.md), [ADR-0003](0003-data-architecture.md), [ADR-0005](0005-kis-token-and-rate-coordination.md)
- 관련 정책: [시장 데이터 및 시점 정책](../spec/market-data-policy.md), [국내 시장 달력 데이터 계약](../data/market-calendar-data-contract.md)

## 배경

KRX 공식 연간 휴장 일정과 임시 거래시간 공지를 합성하는 `collect_krx_market_calendar`, 실전 KIS 국내휴장일조회로 당일 개장 여부를 보완하는 `confirm_today_market_calendar`를 수동 실행할 수 있다. 자동 수집을 시작하려면 두 작업의 실행 순서, 서울 기준 실행 시각, 재시도 범위와 중복 실행 방식을 먼저 고정해야 한다.

Taskiq scheduler는 메시지를 예약하는 역할이며 정확히 한 번 실행을 보장하는 영속 원본이 아니다. scheduler나 worker 재시작, 메시지 재전달과 실수로 실행된 복수 scheduler 때문에 같은 외부 API 호출이 겹칠 수 있다. KRX 재수집은 멱등 저장되지만 불필요한 외부 요청이 발생하고, KIS 확인은 실전 자격증명과 호출 한도를 사용한다. 반대로 한 번의 네트워크 실패를 당일 최종 실패로 확정하면 시장 달력이 `pending` 상태에 머물러 이후 수집이 장시간 차단될 수 있다.

## 결정

### 실행 주체와 시간 기준

- Taskiq scheduler는 배포 전체에서 단일 인스턴스만 실행한다. worker는 필요에 따라 여러 개 실행할 수 있다.
- 모든 영업일 판정과 실행 구간은 `Asia/Seoul` 기준으로 계산한다. 서버와 데이터베이스에는 UTC 시각을 기록한다.
- scheduler는 작업 메시지만 발행하며 KIS 자격증명을 갖지 않는다. 외부 API 호출과 PostgreSQL 갱신은 worker에서 수행한다.
- 로컬 기본 Compose에서는 자동 scheduler와 KIS 당일 확인을 비활성화한다. KRX 자동 수집과 KIS 실전 확인은 서로 독립된 명시적 설정으로 활성화한다.
- 실수로 scheduler가 둘 이상 실행돼도 아래의 PostgreSQL 실행 claim이 실제 중복 작업을 차단해야 한다. 단일 인스턴스 설정만 중복 방지 수단으로 사용하지 않는다.

### 예약 시각과 순서

| 작업 | 서울 기준 실행 창 | 성공 전 재시도 | 논리 실행 키 |
|---|---|---|---|
| KRX 현재 연도 달력 합성 수집 | 매일 05:00부터 06:20까지 | 10분 간격 | `krx-calendar:XKRX:{year}:{local_date}` |
| KRX 다음 연도 달력 합성 수집 | 12월 1일부터 12월 31일까지 같은 창 | 10분 간격 | `krx-calendar:XKRX:{next_year}:{local_date}` |
| KIS 당일 보완 확인 | 매일 06:30부터 15:20까지 | 10분 간격 | `kis-calendar:XKRX:{trading_date}:v{calendar_version}` |

- KRX 현재 연도 수집이 그날 성공하기 전에는 KIS 당일 확인을 실행하지 않는다. 당일 KRX 수집 성공 후 현재 세션 버전을 다시 읽고 KIS 확인을 시작한다.
- 12월에는 현재 연도와 다음 연도를 별도 실행 키로 수집한다. 다음 연도 일정이 아직 발표되지 않아 실패해도 현재 연도 성공을 되돌리지 않는다.
- KRX 작업은 당일 한 번 성공하면 같은 날짜와 대상 연도의 후속 예약을 건너뛴다. 다음 날에는 다시 수집해 새 휴장 일정이나 임시 거래시간 공지를 반영한다.
- KIS 작업은 현재 시장 달력 버전이 이미 `confirmed`이거나 `conflict`이면 외부 호출 없이 종료한다. KRX 정정으로 새 버전이 생성되면 버전이 포함된 새 실행 키로 다시 확인한다.
- KIS 응답이 KRX와 일치하면 `confirmed`, 다르면 `conflict`를 유지하고 해당 버전의 반복 호출을 중단한다. `conflict`는 성공적인 확인 결과이지만 이후 시장 데이터와 전략 실행은 계속 차단한다.
- 네트워크, 파싱, Valkey, 데이터베이스 실패는 실행 창 안에서만 재시도한다. 고정된 실행 창이 끝난 뒤 무한 재시도하거나 다음 날의 작업으로 소급 처리하지 않는다.
- 07:00까지 당일 확인이 완료되지 않으면 기존 데이터 계약대로 지연 상태로 표시한다. 늦게 확인되면 그 시점 이후 작업만 허용하며 놓친 작업을 자동 소급 실행하지 않는다.

### 영속 실행 claim

PostgreSQL `operations` 스키마에 scheduler 실행 claim을 저장한다. 최소 필드는 작업 이름, 논리 실행 키, 상태, lease 만료시각, 시도 횟수, 시작·완료시각과 비밀정보 없는 오류 코드다.

1. worker는 외부 요청 전에 `(task_name, execution_key)` 유일 키로 claim을 원자적으로 획득한다.
2. 같은 키가 `running`이고 lease가 유효하면 중복 메시지를 외부 호출 없이 종료한다.
3. `succeeded` 또는 도메인 종결 결과인 `conflict`는 같은 키로 다시 실행하지 않는다.
4. 실패했거나 lease가 만료된 실행은 예약 창 안에서 다음 메시지가 다시 claim할 수 있다. 회수할 때 시도 횟수를 증가시킨다.
5. worker 비정상 종료를 복구할 수 있도록 lease에는 유한한 만료시간을 둔다. 소유자 토큰이 일치하는 worker만 완료 또는 실패 상태로 전환한다.
6. KRX와 KIS의 기존 저장 멱등성은 마지막 방어선으로 유지한다. 실행 claim이 데이터베이스의 사실 버전, 원본 응답과 동기화 상태를 대체하지 않는다.

예약 메시지와 CLI 수동 실행은 같은 claim 경계를 사용한다. 초기 구현에는 claim을 우회하는 `force` 옵션을 두지 않는다. 과거 연도 백필은 대상 연도와 명시적 백필 실행 식별자를 사용해 일일 자동 실행과 키 공간을 분리한다.

### 후속 작업의 실행 경계

- 시장 데이터, 전략과 주문 작업은 메시지가 예약된 시각이 아니라 실제 실행 직전에 `calendar_schedule_decision`을 다시 호출한다.
- 현재 세션이 없거나 `pending`, `conflict`, 오래된 확인이면 fail-closed로 실행하지 않는다.
- `closed`이면 정상적인 미실행으로 종료하고, `open` 또는 `shortened`일 때만 해당 세션의 `opens_at`과 `closes_at` 범위 안에서 실행한다.
- scheduler 장애, KRX 실패와 KIS 확인 실패는 장이 열린 것으로 추정하는 근거가 될 수 없다. 평일 규칙이나 직전 거래일 값을 대신 사용하지 않는다.

### 활성화 단계

1. scheduler와 실행 claim을 fixture·PostgreSQL·Valkey 환경에서 검증한다.
2. KRX 자동 수집만 활성화해 중복 메시지, 실패 후 재시도와 worker 종료 후 lease 회수를 확인한다.
3. KIS 당일 확인은 실전 읽기 전용 자격증명으로 `CTCA0903R` 실제 응답을 별도 검증한 뒤 사용자가 명시적으로 활성화한다.
4. KIS 자동 확인이 비활성 또는 실패한 동안 시장 데이터와 향후 전략 실행은 기존 시장 달력 판정에 따라 차단된다.

## 대안

### 운영체제 cron에서 두 CLI를 직접 실행

프로세스 배포 경로가 Taskiq와 분리되고 복수 호스트의 중복 실행, 상태 추적과 worker 재사용이 어려워 채택하지 않는다.

### 단일 scheduler 인스턴스만 신뢰

메시지 재전달과 배포 실수로 인한 복수 인스턴스를 막지 못하고 scheduler 재시작 이력도 영속적으로 판단할 수 없어 채택하지 않는다.

### Valkey 잠금만 사용

동시 실행은 줄일 수 있지만 TTL 만료 후 그날 이미 성공한 작업인지 판단할 영속 근거가 없다. Valkey는 업무 상태의 원본이 아니므로 PostgreSQL claim을 채택한다.

### KIS를 06:30에 한 번만 확인

일시적인 KIS 또는 네트워크 장애가 하루 전체의 자동 수집 중단으로 이어진다. 성공 또는 충돌이 확정될 때까지 제한된 실행 창에서 재시도하는 방식을 채택한다.

### 확인 실패 시 KRX 일정만으로 실행

당일 임시 변경과 출처 충돌을 놓칠 수 있고 승인된 fail-closed 데이터 계약을 약화하므로 금지한다.

## 결과

- KRX 수집이 KIS 확인보다 먼저 실행되고 07:00 확인 목표가 명시된다.
- scheduler와 worker가 재시작되거나 메시지가 중복돼도 같은 논리 작업의 외부 호출이 겹치지 않는다.
- 일시 실패는 제한된 구간에서 복구할 수 있고 성공·충돌 후에는 불필요한 KIS 호출을 보내지 않는다.
- 실행 claim을 위한 PostgreSQL 마이그레이션과 저장소, scheduler 프로세스 설정이 추가된다.
- scheduler가 정상이어도 시장 달력 판정이 안전하지 않으면 후속 작업은 실행되지 않는다.

## 구현 기록

2026-08-16에 `operations.scheduled_job_run`, 9분 lease와 소유자 토큰 기반 claim 저장소, 서울 기준 Taskiq 예약과 단일 Compose scheduler 프로필을 구현했다. 기본 Compose에서는 scheduler가 시작되지 않으며 `calendar-scheduler` 프로필은 KRX 예약만 명시적으로 활성화하고 KIS 비밀정보를 받지 않는다. 같은 날 실전 읽기 전용 `CTCA0903R` 응답과 중복 차단을 수동 검증했다. KIS 예약은 `live` 환경과 별도 활성화 플래그가 모두 필요하며 사용자가 명시적으로 활성화하기 전까지 꺼져 있다.

## 완료 기준

- 단일 Taskiq scheduler가 서울 기준 예약을 발행하고 배포 설정에서 복제 수가 1로 고정된다.
- 같은 논리 실행 키의 메시지를 동시에 둘 이상 전달해도 외부 어댑터 호출은 한 번만 발생한다.
- 성공한 실행은 같은 날짜의 후속 tick에서 외부 호출 없이 종료한다.
- 실패와 worker 종료는 실행 창 안에서 재시도되고 유효 lease가 있는 실행은 가로채지 않는다.
- KRX 성공 전 KIS 확인, 모의환경 KIS 확인과 확인되지 않은 세션의 후속 수집이 모두 차단된다.
- KRX 정정으로 시장 달력 버전이 바뀌면 새 버전에 대해 KIS 확인을 다시 수행한다.
- 실전 KIS 자동 확인은 실제 읽기 전용 검증과 사용자 활성화 전까지 꺼져 있다.
- Ruff, basedpyright, 백엔드 테스트, PostgreSQL·Valkey 통합 테스트, Compose 계약 검사와 문서 검사가 통과한다.

## 재검토 조건

- KRX 또는 KIS의 공지·휴장일 제공 시각이나 호출 제한이 변경된다.
- 여러 거래소 또는 여러 실전 계좌를 동시에 운영한다.
- scheduler를 고가용성 구성으로 전환하거나 PostgreSQL claim의 처리량이 병목이 된다.
- 분봉·실시간 수집이 추가되어 장중 작업 우선순위와 재처리 정책을 별도로 조정해야 한다.
