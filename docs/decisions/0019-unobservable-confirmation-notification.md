# ADR-0019: 확인을 받을 수 없는 노출 축소 요청의 알림 경계

- 상태: 승인 (2026-08-25 구현)
- 결정일: 2026-08-25
- 승인: 2026-08-25 사용자 승인("초안대로"). 질문 1·2·4는 초안대로 확정했다 — 예외를 `cancel_failed`로
  한정하고, 기록 시점은 요청 **전**이며, 심각도는 경고다. **질문 3은 구현 중 답이 바뀌었다**: 정정
  경로는 이미 리스너 없으면 거부하므로(`LISTENER_NOT_ATTACHED`) 대상에 넣을 것이 없다(아래 §구현)
- 관련 결정: [ADR-0014 주문·위험 이벤트 외부 알림 경계](0014-outbound-event-notification.md), [ADR-0013 미체결 수량 축소 경계 (부분 취소)](0013-paper-partial-cancel.md), [ADR-0009 실시간 체결통보 수신 경계](0009-realtime-fill-notification.md), [ADR-0017 마감 후 재대조와 세션 종료 주문 처리 경계](0017-post-close-reconciliation-and-session-end.md)
- 관련 정책: [거래 안전 정책](../spec/trading-safety-policy.md)
- 관련 계약: [주문·위험 이벤트 외부 알림 계약](../data/event-notification-contract.md), [실시간 체결통보 계약](../data/realtime-fill-notification-contract.md)

## 배경

인계 문서에 "부분취소 요청이 확인 알림 없이 끝나면 푸시로 전혀 보이지 않는다 — 알림 필터를 넓힐지
결정이 필요하다"고 남겼다. 실데이터를 재보니 **문제가 필터가 아니었다.**

## 측정한 사실 (2026-08-25)

### 1. 취소 확인은 대체로 즉시 온다 — 우리 요청 기록보다 먼저 오기도 한다

상태를 바꾸지 않는 주문 이벤트는 전 기간 19건이다(`cancel_requested` 13, `cancel_failed` 2,
`order_revised` 2, `partial_cancel_requested` 1, 상태 무변화 `FILL_NOTIFICATION` 1).

취소 요청 대부분은 곧바로 확인 통보를 받았다. 그 정도가 아니라 **통보가 우리 요청 기록보다 먼저 적용된
사례가 있다.**

```
0000026443  seq 3  submitted -> canceled   FILL_NOTIFICATION   13:07:54
            seq 4  canceled  -> canceled   cancel_requested    13:07:49   (EMERGENCY_STOP)
```

시각은 앞선 요청이 시퀀스는 뒤다. 증권사가 HTTP 응답보다 통보를 먼저 밀어주는 기록된 성질이 취소에도
같이 나타난다. 따라서 "요청했는데 확인이 안 온다"는 것은 **일반적인 상태가 아니다.**

### 2. 확인이 오지 않은 단 한 건은 리스너가 없을 때 요청됐다

```
09:33:06  LISTENER_DETACHED
09:33:54  0000009931  cancel_requested (EMERGENCY_STOP)   ← 48초 뒤
```

통보는 재생되지 않는다(ADR-0009). 그래서 이 취소의 확인은 **영구히 유실됐다.** 그 주문은 장이 끝날
때까지 `submitted`로 남았고, ADR-0017의 세션 종료 종결이 21:36에야 `expired`로 정리했다. 즉 사람은
**12시간 동안 "취소했다고 믿는 주문이 실제로는 살아 있을 수 있는 상태"를 알 수 없었다.**

### 3. 노출 축소 경로는 리스너 검사를 의도적으로 면제한다

리스너 부착 검사(`_block_code`)는 **제출 경로에만** 걸린다. 비상정지(`cancel_open_orders`)와 부분
취소(`reduce_open_quantity`)는 검사하지 않는다 — ADR-0013이 "노출을 줄이는 행위는 어떤 한도도 새로
위반할 수 없고, 막으면 사람의 위험 축소 수단을 빼앗는다"고 정한 결과다. **그 결정은 옳다.** 문제는 그
면제의 부작용이 아무 곳에도 드러나지 않는다는 것이다.

### 4. 취소 실패는 상태 변화가 없어서 푸시에서 빠진다

```
0000008637  cancel_failed  40330000  →  최종 filled
0000008645  cancel_failed  40330000  →  최종 filled
```

비상정지가 취소를 시도했고 증권사가 거절했다(이미 체결돼 취소할 수량이 없었다). **사람이 알아야 하는
소식인데** 상태가 바뀌지 않았으므로 알림 선별에서 제외됐다. 요청과 실패는 성질이 다른데 같은 규칙에
묶여 있다.

## 문제의 재정의

원래 항목은 "요청을 알릴지"였다. 측정 결과 알려야 하는 것은 요청이 아니다 — 사람이 방금 CLI로 실행한
행동은 소식이 아니다. 알려야 하는 것은 두 가지다.

1. **확인을 받을 수 없는 상태에서 요청이 나갔다**는 사실. 요청은 성공했지만 그 결과를 관측할 수단이
   없다. 이것이 오늘 12시간의 공백을 만들었다.
2. **요청이 실패했다**는 사실. 증권사가 거절했으므로 노출이 줄지 않았다.

둘 다 사람이 행동할 수 있다 — 리스너를 붙이거나, 주문 상태가 마감까지 미확인임을 알고 대응한다.

## 결정

### 1. 알림 선별 규칙은 그대로 둔다 — 상태 변화만 알린다

`is_notifiable`의 `previous_state != state` 요구를 유지한다. 요청 이벤트를 전부 알리면 사람이 방금 한
행동이 푸시로 되돌아오고, 실제 소식이 그 사이에 묻힌다. ADR-0014의 "사람이 행동할 수 있는 이벤트"
기준을 그대로 적용한 결과다.

### 2. 요청 실패는 예외로 둔다

`cancel_failed`는 상태가 바뀌지 않아도 알린다. **노출을 줄이려 했는데 줄지 않았다**는 사실이며 사람이
다른 수단을 써야 한다. 심각도는 경고다.

예외는 사유 코드로 좁게 지정한다. "상태가 안 바뀐 이벤트를 전부 알린다"로 넓히지 않는다.

### 3. 확인을 받을 수 없는 요청은 문제로 기록하고 알린다

노출 축소 요청(비상정지 취소·부분 취소)을 보낼 때 리스너가 붙어 있지 않으면, 요청 자체는 그대로
보내고 **새 사유 코드 `CONFIRMATION_UNOBSERVABLE`로 재조정 문제를 기록한다.** 그 문제 이벤트가 기존
알림 경로를 타고 경고로 나간다.

기록 시점은 요청 **전**이다. 요청이 나간 뒤에 기록하면 요청과 기록 사이에 프로세스가 죽었을 때 아무
기록도 남지 않는다.

### 4. 요청을 막지 않는다

리스너가 없다는 이유로 비상정지나 부분 취소를 거부하지 않는다. ADR-0013의 근거가 그대로 유효하다 —
노출을 줄이는 행위는 어떤 한도도 새로 위반할 수 없고, 막으면 사람의 마지막 통제 수단을 빼앗는다.
**특히 비상정지는 일이 잘못되고 있을 때 쓰는 수단이고, 리스너가 죽어 있는 것이 바로 그 이유일 수
있다.** 막는 대신 알린다.

### 5. 이 문제는 게이트의 미조정 판정에 들어간다

`CONFIRMATION_UNOBSERVABLE`은 `reconcile_problem` 유형이므로 ADR-0018의 규칙을 그대로 따른다 — 참조
주문이 종결되면 자동으로 해소되고, 종결되지 않으면 미조정으로 남는다. 별도 예외를 만들지 않는다.

## 결과

- 오늘 같은 12시간 공백이 요청 시점에 즉시 드러난다.
- 취소 실패가 푸시로 나간다. 지금은 감사 기록을 직접 열어야만 보인다.
- 알림 볼륨은 거의 늘지 않는다. 실측 기준으로 예외 대상은 전 기간 3건이다(`cancel_failed` 2 + 리스너
  없는 요청 1). 요청 전부를 알리는 방식은 19건이 된다.
- 비용: 새 사유 코드 하나, 축소 경로 두 곳의 사전 검사, 알림 선별의 좁은 예외 하나.

## 대안

### A. 요청 이벤트를 전부 알린다

원래 항목이 제안한 방향이다. 채택하지 않는다 — 사람이 방금 한 행동을 되돌려 보내는 알림이 대부분이고
(19건 중 16건), 그 사이에 실제 소식이 묻힌다. 알림이 많아지면 읽지 않게 되고, 읽지 않는 알림은 없는
알림과 같다.

### B. 리스너가 없으면 노출 축소를 막는다

확인할 수 없는 요청을 애초에 만들지 않는다는 논리다. 채택하지 않는다 — 비상정지를 막는 설계는 어떤
이유로도 정당화되지 않는다. 리스너 장애와 시장 급변이 같이 오는 경우가 정확히 비상정지가 필요한
상황이다.

### C. 요청 후 N초 기다려 확인이 오는지 본다

가장 정확하지만 CLI가 대기하게 되고, 리스너가 없으면 어차피 확인은 오지 않는다. 리스너 부착 여부는
요청 전에 이미 알 수 있으므로 기다릴 이유가 없다. 리스너가 **붙어 있는데도** 확인이 오지 않는 경우는
아직 관측되지 않았으므로, 관측되면 그때 이 대안을 다시 본다.

### D. 마감 후 종결에 맡긴다

현 상태다. ADR-0017이 세션 종료 시 정리하므로 사실은 결국 드러난다. 채택하지 않는다 — 오늘 그 지연이
12시간이었고, 그 사이 "취소했다고 믿는 주문"이 체결될 수 있었다.

## 승인이 필요한 질문 (모두 답을 받았다 — 2026-08-25)

1. **결정 2의 예외를 `cancel_failed`로 한정하는가?** 다른 실패 코드(예: 정정 실패)가 생기면 같은
   방식으로 하나씩 추가하는 것이 초안의 의도다. "실패는 전부"로 넓히면 아직 없는 코드까지 미리
   허용하게 된다.
2. **결정 3의 기록 시점(요청 전)을 받아들이는가?** 요청 전에 기록하면 요청이 실제로 나가지 않았는데
   문제가 남는 경우가 생길 수 있다. 초안은 그 편을 택한다 — 기록 없는 요청보다 요청 없는 기록이 안전하다.
3. **정정도 결정 3의 대상에 넣는가?** 초안은 포함한다고 적었다. → **넣을 것이 없다.** 구현 중 확인해
   보니 정정 경로는 이미 리스너가 없으면 거부한다(`revision.py`의 `LISTENER_NOT_ATTACHED`, 회귀
   테스트도 있다). 정정은 노출 축소가 아니라 가격을 바꿔 체결 확률을 올릴 수 있으므로 그 차단이 맞고,
   ADR-0013의 면제 근거("노출을 줄이는 행위는 어떤 한도도 새로 위반할 수 없다")가 정정에는 적용되지
   않는다. **초안이 확인하지 않은 가정이었다.**
4. **심각도를 경고로 두는가?** `CONFIRMATION_UNOBSERVABLE`과 `cancel_failed` 모두 경고를 제안한다.

## 미측정

- 리스너가 붙어 있는데도 취소 확인이 오지 않는 경우. 아직 관측되지 않았다(오늘 1건은 리스너가 없었다).
  관측되면 대안 C를 다시 본다.
- 정정 확인 통보의 실제 도착 여부. `order_revised` 2건 모두 리스너가 붙어 있었으나 정정 확인은 상태를
  바꾸지 않으므로 이벤트로 남지 않아 도착을 확인할 수 없다.

## 재검토 조건

- 실전 전환 시 결정 6을 다시 판단한다.
- `CONFIRMATION_UNOBSERVABLE`이 반복해서 쌓이면 리스너 운영이 불안정하다는 신호다. 알림을 늘릴 문제가
  아니라 리스너를 상시 가동으로 만들 문제다.

## 구현 (2026-08-25)

승인 당일 구현했다.

- 새 사유 코드 `ReconcileProblem.CONFIRMATION_UNOBSERVABLE`.
- `OrderSubmitter._warn_unobservable`이 리스너 부착을 확인하고, 붙어 있지 않으면 재조정 문제를
  **요청 전에** 남긴다. 비상정지 취소(`cancel_open_orders`, 주문마다)와 부분 취소
  (`reduce_open_quantity`)가 호출한다. 요청은 그대로 나간다.
- 알림 선별에 좁은 예외를 뒀다: `_NOTIFIABLE_ORDER_REASONS = {"cancel_failed"}`. 이 사유는 상태가
  바뀌지 않아도 알리고 심각도는 경고다. 요청 이벤트(`cancel_requested`·`partial_cancel_requested`·
  `order_revised`)는 그대로 제외된다 — 테스트가 그 셋을 명시적으로 고정한다.

### 질문 3의 답이 바뀐 이유

초안은 정정을 대상에 포함했다. 구현하려고 코드를 열어 보니 정정은 이미 리스너 없이는 거부된다. 정정은
가격을 바꿔 체결 확률을 올릴 수 있으므로 노출 축소가 아니고, ADR-0013의 면제 근거가 적용되지 않는다.
**초안이 확인하지 않은 가정이었고, 구현이 그것을 잡았다.** 결과적으로 결정 3의 대상은 비상정지 취소와
부분 취소 둘이다.

### 실데이터 검증 (2026-08-26 09:06~09:13 KST)

리스너를 붙여 한국전력(015760) 15주씩 2건을 기준가 3% 아래 지정가(33,500원)로 제출해 미체결로 두고,
**리스너를 끈 뒤** 비상정지를 실행했다.

```
09:10:18  0000006251 / 0000006274  planned → submitted  (40600000)
09:12:38  listener detached
09:12:38  --emergency-stop  →  state=emergency_stop cancel_requested=2 cancel_failed=0
09:12:39  CONFIRMATION_UNOBSERVABLE  0000006251
09:12:39  CONFIRMATION_UNOBSERVABLE  0000006274
```

결정대로다 — 요청은 **막히지 않고 나갔고**(`cancel_requested=2`), 주문마다 하나씩 기록됐으며, 확인이
올 수 없으므로 두 주문은 `submitted`로 남았다. 알림도 경고로 발신됐다.

**매수는 밴드 상한만 검사한다**는 성질을 이용해 체결되지 않는 주문을 만들었다(`--price-offset-pct -3`).
삼성전자로 먼저 시도했을 때는 어제 보유분 3주 때문에 `RISK_SYMBOL_EXPOSURE`로 거절됐다 — 종목 한도가
의도대로 동작한 것이므로 보유가 없는 종목으로 바꿨다.

### 이 실측이 잡은 결함 (수정 완료)

발신된 경고의 본문이 이랬다.

```
[reconcile_problem] CONFIRMATION_UNOBSERVABLE
09:12:39 KST
```

**어느 주문인지가 없다.** 두 메시지가 구별되지 않아 사람이 행동할 수 없고, 머리말도 코드 이름이 그대로
나갔다. 원인은 투영에 있었다 — 자동매매 이벤트는 `broker_order_id=None`으로 고정되고 재조정 문제의
`detail`(주문 참조)이 버려진다. 계약의 공개 범위는 증권사 주문번호를 보내는 필드로 이미 규정하므로
**결함 수정**이다(승인 필요 없음).

고친 뒤 같은 이벤트의 본문:

```
[대조 불일치] CONFIRMATION_UNOBSERVABLE
증권사 주문 0000006251
09:12:39 KST
```

재조정 문제의 상세만 본문에 넣는다 — 다른 유형(`attestation` 등)의 상세는 사람이 쓴 자유 문구라 금지
필드가 섞일 수 있다. 머리말은 종류별 한국어 표를 뒀다.

**이미 발신된 2건은 옛 본문 그대로다.** 아웃박스는 투영 시점의 본문을 보관하며 재작성하지 않는다.

### 미측정

- `cancel_failed` 알림의 실제 발신. 과거 2건은 알림 도입 전이라 아웃박스에 없고, 오늘은 취소 요청이
  전부 접수돼(`cancel_failed=0`) 발생하지 않았다.
