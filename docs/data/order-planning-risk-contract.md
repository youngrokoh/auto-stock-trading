## 목적

전략 신호를 모의투자 주문 계획으로 바꾸는 경로에서 계좌 상태, 목표 포지션, 위험검사 판정, 주문
식별과 감사 기록의 정의를 고정한다. 이 계약의 범위는 `PLANNED` 주문 생성까지이며 증권사 주문
제출은 포함하지 않는다.

## 원칙

1. **정책이 상한이다.** 모든 한도는 [거래 안전 정책](../spec/trading-safety-policy.md) §3·§4의 값을
   그대로 사용한다. 코드·설정·화면에서 완화할 수 없고, 여러 한도가 겹치면 가장 엄격한 결과를 쓴다.
2. **결정적 판정.** 위험검사는 외부 호출 없는 순수 함수이며 같은 입력에 같은 판정을 낸다. 난수와
   실행 시각 의존이 없고, 시각은 입력으로 받는다.
3. **fail-closed.** 판정에 필요한 사실이 없거나 오래됐으면 주문을 만들지 않고 사유 코드를 남긴다.
   조회는 막지 않고 주문 생성만 막는다.
4. **감사 가능.** 주문마다 전략·신호 버전, 기준 데이터 출처와 시각, 적용된 모든 위험 규칙의
   한도값·예상값·통과 여부, 상태 전이 이력을 보존한다.
5. **비밀정보 분리.** 계좌번호·상품코드 원문은 저장·응답·로그에 남기지 않고 해시 참조만 쓴다.
   주문·계좌 경로에는 모의 자격증명만 주입한다.
6. **금액은 `Decimal`, 수량은 정수.** 시각은 UTC 저장·서울 해석이다.

## 계좌 스냅샷

`trading.account_snapshot`은 append-only이며 한 번의 조회 결과를 한 행으로 남긴다. 보유 종목은
`trading.account_position`에 스냅샷별로 저장한다.

| 필드 | 의미 |
|---|---|
| `account_reference` | `sha256(계좌번호 + 상품코드)`의 앞 12자 hex. 원문은 저장하지 않는다 |
| `cash_balance` | 예수금 총액 |
| `orderable_cash` | 주문 가능 현금. 잔고조회의 가수도정산금액(D+2 예수금)을 사용하고, 종목별 매수가능조회는 주문 제출 단계에서 최종 확인한다 |
| `position_value` | 보유 종목 평가금액 합계 |
| `nav` | `cash_balance + position_value`. 우리 계산값이며 증권사 순자산금액과 대조한다 |
| `broker_net_asset` | 증권사가 보고한 순자산금액 (대조용, 판정에는 쓰지 않는다) |
| `as_of` / `received_at` | 증권사 기준시각과 수신 시각 |

- 장 시작 NAV는 해당 거래일 최초 성공 스냅샷의 `nav`로 고정한다(정책 §2).
- 고점 NAV는 저장된 스냅샷 `nav`의 최댓값이다.
- 스냅샷이 없거나 계획 실행보다 오래된 거래일 것이면 계좌 조정 미완료로 판정한다.

## 목표 포지션

전략 신호(`buy`/`sell`)를 목표 비중으로 바꾸는 규칙은 승인된 정책 한도를 상한으로 쓴다.

```text
매수 신호 → 목표 비중 = 종목별 한도 (NAV의 10%)
매도 신호 → 목표 비중 = 0%
목표 금액 = NAV × 목표 비중
필요 금액 = 목표 금액 − 현재 평가금액(기준가 × 보유 수량)
```

- 필요 금액이 0 이하인 매수와 보유 수량이 0인 매도는 주문을 만들지 않는다(`NO_CHANGE`).
- 주문 1건 한도(NAV의 5%)를 넘는 필요 금액은 각 건이 한도 이하가 되도록 분할한다. 분할 주문도
  동시 미체결 한도(5건)에 포함된다.
- 매도 수량은 보유 수량과 주문 가능 수량 중 작은 값을 넘지 않는다. 공매도·신용·미수는 없다.
- 백테스트(가용 현금 전량 매수)와 수량·성과가 다르다. 백테스트에 같은 사이징을 적용하는 작업은
  후속이며, 두 경로의 차이를 검증 문서에 기록한다.

## 기준가와 지정가

- 기준가는 계획 실행 시점에 새로 조회한 KIS 현재가만 사용한다. 배치 수집 시세·일봉은 쓰지 않는다.
- 기준가 수신 후 10초를 넘기면 `DATA_STALE`로 차단한다(정책 §4).
- 초기에는 지정가만 허용한다. 지정가는 기준가를 호가단위로 반올림한 값이며, 반올림 후 매수는
  기준가의 +1% 초과, 매도는 −1% 미만이면 `RISK_ORDER_PRICE_BAND`로 거절한다.
- 노출 계산의 평가금액은 계획 시점 기준가 × 수량을 사용한다. 스냅샷 평가금액은 대조용이다.

호가단위는 KRX 규정을 코드 상수로 고정한다. ETF·ETN은 가격 구간과 무관하게 5원이다.

| 주식 가격 구간 | 호가단위 |
|---|---:|
| 2,000원 미만 | 1원 |
| 2,000원 이상 5,000원 미만 | 5원 |
| 5,000원 이상 20,000원 미만 | 10원 |
| 20,000원 이상 50,000원 미만 | 50원 |
| 50,000원 이상 200,000원 미만 | 100원 |
| 200,000원 이상 500,000원 미만 | 500원 |
| 500,000원 이상 | 1,000원 |

## 위험 규칙

정책 §3의 한도를 규칙 코드로 고정한다. `기준`은 판정에 쓰는 값이고, `초과 시`는 정책이 정한 동작이다.
비중 검사는 체결된 포지션과 미체결·계획 주문이 모두 체결된다고 가정한 예상 노출로 한다(정책 §2).

| 규칙 코드 | 한도 | 초과 시 |
|---|---:|---|
| `RISK_TOTAL_EXPOSURE` | NAV의 80% | 해당 매수 거절 |
| `RISK_MIN_CASH` | NAV의 20% | 해당 매수 거절 |
| `RISK_SYMBOL_EXPOSURE` | NAV의 10% | 해당 주문 거절 |
| `RISK_SECTOR_EXPOSURE` | NAV의 30% | 해당 주문 거절 |
| `RISK_UNCLASSIFIED_EXPOSURE` | NAV의 10% | 해당 주문 거절 |
| `RISK_ORDER_AMOUNT` | NAV의 5% | 분할 후 남으면 거절 |
| `RISK_DAILY_BUY_AMOUNT` | 장 시작 NAV의 20% | 이후 신규 매수 거절 |
| `RISK_OPEN_ORDERS` | 5건 | 추가 주문 거절 |
| `RISK_DAILY_ORDER_ATTEMPTS` | 20건 | 자동매매 일시정지 |
| `RISK_DAILY_LOSS` | 장 시작 NAV 대비 −2% | 자동매매 일시정지 |
| `RISK_DRAWDOWN` | 고점 NAV 대비 −5% | 자동매매 일시정지 |
| `RISK_CONSECUTIVE_REJECTS` | 연속 3건 | 자동매매 일시정지 |
| `RISK_API_FAILURES` | 5분 내 3회 | 자동매매 일시정지 |

정책 §4의 주문 가능 조건 중 수량·가격에 직접 작용하는 것도 같은 형식의 규칙으로 판정한다.

| 규칙 코드 | 한도 | 초과 시 |
|---|---|---|
| `RISK_ORDERABLE_CASH` | 증권사 주문 가능 현금 | 해당 매수 거절 |
| `RISK_ORDERABLE_QUANTITY` | 보유 수량과 주문 가능 수량의 최솟값 | 해당 매도 거절 |
| `RISK_ORDER_PRICE_BAND` | 기준가 ±1% | 해당 주문 거절 |

- 업종 분류 데이터가 없는 종목은 모두 미분류로 취급하고 합계에 `RISK_UNCLASSIFIED_EXPOSURE`를
  적용한다. 업종 분류가 없다는 이유로 업종 한도를 생략하지 않는다(정책 §3).
- 기준가가 없는 보유 종목의 노출은 스냅샷 평가금액으로 계산한다. 노출을 낮추지 않기 위한 규칙이다.
- 동시 미체결 한도로 만들지 못한 잔여 수량은 주문하지 않고 다음 계획에서 다시 평가한다.
- **현재 유니버스는 전 종목이 미분류라 총 노출의 실질 상한이 NAV의 10%다.** 이는 정책 그대로의
  보수적 결과이며 완화에는 업종 분류 수집과 사용자 결정이 필요하다.
- 일시정지 규칙에 걸리면 계획 전체를 만들지 않고 자동매매 상태를 `PAUSED`로 전이한다.

## 차단 사유 코드

정책 §7.2의 코드를 화면·감사·API가 같은 문자열로 사용한다.

| 코드 | 판정 |
|---|---|
| `MARKET_CLOSED` | 검증된 달력의 거래일이 아니거나 주문 허용시간(09:05~15:15 Asia/Seoul) 밖 |
| `DATA_STALE` | 기준가 수신 후 10초 초과 또는 기준가 조회 실패 |
| `ACCOUNT_NOT_RECONCILED` | 당일 계좌 스냅샷이 없거나, 증권사와 대조되지 않은 미체결 주문이 내부에 존재 |
| `SYMBOL_SUSPENDED` | 종목 거래 상태가 정상이 아님 |
| `API_CONSECUTIVE_FAILURE` | 5분 내 외부 API 3회 실패 |
| `SOURCE_TIMEOUT` | 계획 실행 중 외부 출처 응답 없음. 이 단계에서는 실패를 `automation_event`의 `api_failure`로 기록하고 실행을 중단하며 계획 행을 만들지 않는다 |

`AUTOMATION_NOT_RUNNING`은 자동매매 상태가 `RUNNING`이 아닐 때의 계획 차단 사유이며, 정책 §6의
상태 자체를 함께 기록한다.

## 주문과 식별자

`trading.order`는 주문당 현재 상태 한 행이며, 이 계약의 범위에서는 `PLANNED`와 `REJECTED`만
생성된다.

```text
PLANNED -> SUBMITTED -> PARTIALLY_FILLED -> FILLED
                    \-> REJECTED
                    \-> CANCELED
```

- 전이는 위 그래프만 허용하고 그 외는 오류다. `PLANNED -> REJECTED`, `PLANNED -> CANCELED`도
  허용한다(제출 전 거절·철회).
- `client_order_id`는 `sha256("전략|전략버전|신호일|종목|구분|순번")`의 앞 32자 hex이며 UNIQUE다.
  같은 신호를 다시 계획해도 같은 식별자가 나오므로 중복 주문이 구조적으로 차단된다. 이 식별자는
  내부 전용이며 증권사 주문 API는 자체 주문번호를 반환한다.
- 주문은 계획(`order_plan`), 계좌 스냅샷, 기준가 출처·시각, 전략·신호 버전을 참조한다.
- `trading.order_event`는 상태 전이와 사유를 append-only로 남긴다. 거절 주문도 규칙 판정과 함께
  보존한다.
- `trading.risk_decision`은 주문별로 규칙 코드·한도값·예상값·통과 여부를 남긴다. 계획 전체가
  차단된 경우에는 주문 없이 계획에 사유 코드를 남긴다.

## 자동매매 상태

정책 §6의 상태와 전이를 그대로 구현한다.

```text
DISABLED -> ARMED -> RUNNING -> PAUSED
    |          |         |          |
    +----------+---------+----------+-> EMERGENCY_STOP
```

- `PAUSED -> ARMED`는 사용자가 원인을 확인한 뒤에만 허용한다. `EMERGENCY_STOP -> DISABLED`는
  사용자 해제다. 그 외 역방향 전이는 오류다.
- 프로세스 시작, 거래일 변경, 자격증명 환경 변경 시 상태는 `DISABLED`로 복귀한다.
- 비상정지는 신규 주문을 금지하고 미체결 취소를 시도하되 보유 포지션을 자동 청산하지 않는다.
- 상태 변경은 `trading.automation_event`에 사유 코드와 함께 append-only로 남긴다. 외부 API 실패도
  같은 테이블에 기록해 `RISK_API_FAILURES` 판정 입력으로 사용한다.

## 저장 테이블

```text
trading
├─ account_snapshot      (append-only 계좌 스냅샷)
├─ account_position      (스냅샷별 보유 종목)
├─ automation_state      (환경별 현재 상태 1행)
├─ automation_event      (append-only 상태 전이·API 실패)
├─ order_plan            (계획 헤더, 차단 사유 포함)
├─ order                 (주문당 현재 상태 1행, client_order_id UNIQUE)
├─ order_event           (append-only 상태 전이)
└─ risk_decision         (주문별 규칙 판정)
```

## 필수 조회 계약

읽기 API는 다음을 제공하며 계좌번호 원문을 절대 노출하지 않는다.

| 경로 | 응답 |
|---|---|
| `GET /api/trading/automation` | 현재 자동매매 상태와 최근 이벤트 |
| `GET /api/trading/account-snapshots` | 계좌 스냅샷 목록(해시 참조·NAV·현금·평가금액과 보유 종목) |
| `GET /api/trading/order-plans` | 계획 목록(생성 시각, 상태, 차단 사유 코드, 주문 수) |
| `GET /api/trading/order-plans/{plan_id}` | 계획 상세와 주문·규칙 판정 전체 |

차단된 계획도 사유 코드와 함께 조회된다. 응답은 항상 기준 데이터의 출처와 시각을 포함한다.

## 검증 조건

- 정책 §8대로 각 한도의 경계값 바로 아래·같음·초과 시나리오를 테스트로 검증한다.
- 오래된 데이터, 계좌 미조정, 거래정지, 장 마감, 자동매매 비활성 상태에서 주문이 생성되지 않는다.
- 같은 신호를 두 번 계획해도 주문이 늘지 않는다(UNIQUE 제약 + 멱등 재계획).
- 모든 거절 사유가 감사 기록과 API 응답에서 같은 코드로 식별된다.

## 이 단계의 한계 (기록)

- 증권사 주문 제출·정정·취소·체결 동기화는 다음 단계다. 따라서 `ACCOUNT_NOT_RECONCILED`는
  "내부에 제출 이후 상태의 주문이 존재하면 차단"으로 판정하며, 실제 증권사 미체결 목록 대조는
  다음 단계에서 구현한다.
- KIS 계좌 조회 응답 필드는 공식 문서 기준으로 구현했고 실계좌 응답 대조는 계좌번호 secret 파일
  제공 후 수행한다. 필드 불일치는 엄격 파싱으로 즉시 실패한다.
