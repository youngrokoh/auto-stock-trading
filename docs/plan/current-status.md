## 반드시 기억할 디자인 상태

- 사용자는 2026-08-12에 [클로드 화면 디자인 사양](../design/claude-design/screen-design-spec.md)과 [HTML 시안](../design/claude-design/screen-mockups.html)을 공식 디자인 방향으로 승인했다.
- 2026-08-17에 승인 토큰·프리미티브(좌표 셀, 데이터 표, 상태 배지, 경고 배너, 반응형 앱 셸)와 운영 개요(`/`), 시장 데이터(`/market`), 구성요소 갤러리(`/showcase`)를 승인 디자인으로 구현했고 390·768·1360px 실브라우저 QA를 통과했다([3단계 검증](../qa/phase-3-market-dashboard-verification.md)). 태블릿 접기 규칙은 같은 날 사용자가 확정했다(레일 유지·내비 숨김·1열·KPI 3×2).
- 시안의 가격, 수익률, 계좌, 주문과 포지션 숫자는 레이아웃 예시이므로 하드코딩하지 않는다. 모든 표시 값은 실제 API에서 오고, 백엔드가 없는 영역은 값 생성 없이 빈 상태 규칙으로 표시한다.
- 이후 화면(기업 분석, ETF 탐색, 전략 연구, 모의매매 콘솔 등)도 같은 토큰과 프리미티브로 확장한다.

95. 주의: **같은 데이터 개선이 두 전략을 반대 방향으로 움직였다.** 같은 창(2023-09-05~2026-08-14)에서 `composite-rank`는 +208.06% → **+253.99%**(MDD −46.51% → −37.46%)로 처음 벤치마크(+240.14%)를 넘었고, `ml-rank`(`lgbm-fund` v4, 표본 95,418·유니버스 138)는 +119.49% → **+90.48%**로 내려갔다. 구간 지표도 갈렸다(IC 0.0297 → 0.0341 상승, 상위 K 초과수익·적중률 하락). 단정할 것 세 가지: v3 모델의 +119.49%는 결함 있는 입력의 값이므로 더 인용하지 않고, 재무 특징이 가격 특징만 쓴 모델(+79.72%, 이번 개선에 영향 없음)을 넘는다는 결론은 살아남았고, 규칙형과의 격차는 119%p → 164%p로 벌어졌다. **입력을 바꿀 때마다 비교 기준을 같은 데이터로 다시 돌려야 한다** — 접두 수정 때는 규칙형이 우연히 영향을 받지 않았지만 이번에는 받았다
96. 완료: 사용자가 2026-08-23 승인한 **우선주 반영 설계 4건**을 구현·실데이터 검증했다. (1) 상장 주식종류를 `reference.share_class` 버전 사실로 적재한다(리비전 `20260823_0027`). 출처는 유니버스와 같은 비인증 KIS 마스터이고 짝짓기는 단축코드 앞 5자리다 — 실측으로 보통주 804·우선주 110, 접두 공유 군 95개 전부에서 보통주가 정확히 하나이며 고아 우선주 0개다. 예외는 fail-closed로 거부하고 보고한다(실수집 `groups=804 new_versions=914 refused=0`). (2) 시가총액은 `market_cap`(보통주)과 `market_cap_total`(전종목)을 함께 노출하고 클래스별 내역(가격·기준시각·거래량·주식수)을 담는다 — **이전 표기는 실제의 90.8%였다**(삼성전자 보통주 1,645.7조 + 우선주 166.1조 = 1,811.8조). 클래스가 하나라도 빠지면 합계는 `MISSING_CLASS_QUOTE`로 만들지 않는다. (3) BPS·PBR은 우선주가 없는 회사만 계산한다(유니버스 161/200). SK하이닉스 164,979.38원·PBR 10.49를 저장 사실 손계산과 대조했고, 우선주가 있는 39종목은 `PREFERRED_ALLOCATION_REQUIRED`다 — 자본금(par) 차감으로 대체하지 않는다. (4) EPS 결측은 **우선주 미상장 회사만** 복원한다(`no_preferred_class`, FY2019~2022 26건). 우선주가 있으면 두 클래스 EPS 차이가 실측 +219%~-76%까지 벌어져 후보가 1행이어도 증명할 수 없다
97. 기록(결함, 수정): 주식종류 수집이 KOSPI 전 종목에 `reference.instrument` 행을 만들어 종목 목록이 201 → **915**가 됐고 그중 668개가 참조 0인 빈 종목이었다. 사실은 전 종목에 저장하는 것이 맞지만 **종목 행은 시세를 수집하는 대상만** 만들어야 한다. 우선주 스윕이 대상별로 생성하도록 고치고, 참조 0·프로필 없음·2시간 내 생성 조건으로 668개를 삭제해 247개(유니버스 200 + ETF 1 + 우선주 46)로 복구했다
98. 대기(사용자 결정): 우선주 46종목이 종목 목록에 들어오면서 **운영 개요의 상위 10개 미리보기 절반이 우선주**가 됐다. 사실로는 맞지만 전략·주문 대상이 아닌 종목이 미리보기를 차지한다. 승인 범위 밖이라 화면은 바꾸지 않았고 e2e 단언만 형태 확인으로 완화했다. 미리보기를 보통주로 한정할지 결정이 필요하다
99. 기록(한계): EPS 복원의 우선주 판정은 **오늘의 마스터 파일** 기준이다. 과거 보고서 시점에 우선주가 있었다가 전환·상장폐지된 회사를 구분하지 못한다. 후보 1행 조건이 대부분 걸러내지만(두 클래스가 있었다면 행이 둘이다) 완전한 시점 정합은 아니며, 시점별 상장 이력 원천을 확보하면 교체한다
100. 기록(결함, 수정): 새 조회 저장소가 `create_app`에서 **즉시 연결 풀을 열어** 앱당 엔진이 하나 늘었다. API 테스트는 앱을 12곳에서 만들고 5곳만 lifespan으로 닫으므로, 전체 스위트에서 통합 테스트 하나가 `DBAPIError`로 깨졌다(실측 `max_connections=100`, 실행 중 62 사용). 엔진을 첫 사용까지 만들지 않도록 고친 뒤 전체 스위트가 통과했다. **원인은 정합하는 증거로만 기록한다** — 좁은 조합으로는 재현되지 않았고 각 방향 관측이 1회씩이다. 다만 첫 실패는 다른 테스트에서 났고(무작위 피해자 = 자원 압박의 특징) 쓰지 않는 저장소가 풀을 여는 것은 그 자체로 잘못이다
101. 기록(교훈): `uv run pytest -q | tail`은 **pytest 종료 코드를 감춘다** — 파이프의 코드가 보고된다. 이 세션에서 실패 1건을 '통과'로 잠깐 보고했다. 스위트 결과는 출력을 파일로 남기고 `FAILED` 줄을 세거나 종료 코드를 직접 읽는다
102. 완료: **유니버스 수급 수집과 일일 예약**(사용자가 2026-08-23 Taskiq 스케줄러 방식을 승인). `--collect-universe-investor-flows`가 200종목을 스윕하고(종목당 요청 1회, 약 3.5분) 개별 실패는 종목코드와 함께 보고한다. 실수집으로 현재 버전 6,004행·200종목·2026-07-03~08-21을 적재했다. 예약은 `worker/investor_flow_schedule.py`가 ADR-0006 패턴을 그대로 쓴다 — 07:10·08:10·09:10 KST 시도, PostgreSQL 실행 claim으로 하루 한 번만 성공, 부분 실패는 실패로 남겨 같은 날 재시도가 남는다. 기본은 꺼져 있고 `infra/compose.investor-flow-schedule.yaml`에서만 켜며 **worker에만 모의 자격증명**을 준다(스케줄러는 받지 않는다). 거래일 판정은 하지 않는다 — 휴장일 실행이 멱등이라 놓친 날이 자동 복구되고, 달력을 전제하면 달력 미커버가 축적을 막는다

기업행사 사실 버전 저장소에 이어 OpenDART 현금배당 수집을 완료했다. 실제 삼성전자 2026-04-30 공시 원문을 fixture로 사용해 공시검색·원본 ZIP 수집, `현금ㆍ현물배당결정` 엄격 파싱, 재수집 멱등성과 기재정정의 버전 연결을 PostgreSQL에서 통합 검증했다. 2026-08-17에는 사용자가 발급한 OpenDART 키(`.secrets/dart-api-key`)로 실제 API에서 2026년 배당 3건(566원·372원·374원)을 수집하고 멱등 재수집과 공개 원문 대조까지 검증했다. 같은 날 KODEX 200 분배금을 운용사 공식 API에서 수집해 2024~2026년 이력 11건을 적재했고, 재수집 멱등성과 '26.7월 월말배당 공지문(183원) 대조를 검증했다. 이어 사용자 승인 규칙(KRX T+2 결제, 검증된 달력만 사용)으로 배당·분배락일 확정 경계를 구현해 실제 10건이 `verified`로 확정됐고 2024년 4건은 달력 미커버로 `pending`을 유지한다. 수정계수 계산기와 수정주가 데이터셋 저장소를 구현·통합 검증했으며, 일봉 확정 전의 실데이터 발행 시도는 계약대로 `unconfirmed_bar_in_range`로 차단됐다(실패 기록 보존). 이어 일봉 재조회 확정 흐름을 구현해 실제 KIS 모의환경에서 7월~8월 일봉 64개를 확정했고, KODEX 200 분배락(2026-07-30)을 반영한 `total_return` 데이터셋 등 4건을 실제 발행해 계수와 수정 종가를 수동 대조했다. 2026-08-17에는 계약의 필수 조회 계약을 따르는 읽기 API를 구현했다. 기업행사는 현재·이력·`knowledge_cutoff_at` 시점 조회를, 수정주가는 종목·방식별 최신 발행 데이터셋과 파생 일봉·개별 계수, 데이터셋 ID 조회와 기업행사별 영향 데이터셋 목록을 제공하며, 응답은 방식·기간·지식 기준시각·알고리즘 버전·입력 해시·데이터셋 ID·출처와 비수정 일봉·기업행사 버전 계보를 항상 포함한다. 실제 발행 데이터로 계수 0.9979577032531667, 수정 종가 89422, 수집 이전 cutoff의 빈 응답(미래정보 차단)과 404·422 오류 계약을 검증했다. 같은 날 사용자가 분봉 데이터 계약을 승인해 비수정 1분봉 수집을 구현했다. 검증된 달력이 최신 거래일과 세션 창을 결정하고(휴장일은 직전 거래일, 미커버·충돌은 fail-closed), 구간 종료 후 두 관측이 일치한 분봉만 확정되며, 모의환경 당일분봉 API 한계로 과거 백필은 불가능해 거래일마다 수집한다. 실제로 2026-08-14 세션 분봉 391개씩을 수집·재수집해 전량 확정했고 시가·종가·고저 포락선·원본 누적 거래량이 확정 일봉과 일치했다. 종가 단일가 행의 2배 거래량 반환은 원본 그대로 보존하고 실측 한계로 계약에 기록했다(사용자 승인). 이어서 승인 디자인 기반 3단계 시장 대시보드를 1차 구현했다. 종목 목록 읽기 API(`GET /api/market-data/instruments`)를 추가하고, 승인 토큰·프리미티브 위에 운영 개요와 시장 데이터 화면을 실제 API 데이터로 재구축했으며(배치 수집 시세는 기준시각과 지연 상태를 항상 노출, 미확정 일봉은 지표 계산 제외), 390·768·1360px 실브라우저 QA와 e2e 9건, vitest 16건(SMA·RSI·MACD·볼린저 수치 벡터 포함)을 통과했다. 태블릿 접기 규칙은 사용자가 확정해 디자인 계약에 기록했다. 이어 4단계 첫 단계로 사용자가 승인한 재무제표 데이터 계약에 따라 OpenDART 전체 재무제표 수집을 구현했다. 보고서(사업연도×유형×연결구분) 단위 사실 버전이 접수번호를 근거로 저장되고, 같은 접수번호 재수집은 멱등이며 정정 공시는 이전 버전을 보존한 새 버전이 된다. 실제 키로 삼성전자 14개 보고서(2021~2025 사업보고서, 2026 1분기·반기 × 연결·개별)를 수집해 자산총계와 라인 수를 DART 원문과 대조했고, 미제출 2026 3분기는 계약대로 건너뛰었다. 실수집에서 발견한 두 가지(자본변동표 `ord` 중복, `account_id` 최대 180자)는 사용자 승인으로 계약을 정정해 반영했다(`line_seq` 유일키, `VARCHAR(255)`). 이어 사용자가 승인한 재무 지표 정의 계약(연결·연간 사업보고서 기준, 같은 보고서의 당기·전기 금액만 사용, ROE 지배주주 기준, 가치지표는 상장주식수 정규화 수집 후 후속)에 따라 성장성 3종·수익성 4종·안정성 2종을 백엔드가 조회 시점에 계산하는 읽기 API를 구현했다. 응답은 지표마다 수식·입력 계정과 금액·근거 접수번호를 포함하고, 필요한 계정이 없으면 값 없이 사유 코드를 담는다(개별 재무제표의 ROE가 실제로 `MISSING_ACCOUNT`). 실제 삼성전자 연결 5개년 지표를 DART 원문 금액 수동 재계산과 대조했다(2025 매출액증가율 10.88%, 영업이익률 13.07%, 부채비율 29.94% 등). 승인 디자인 기업 분석 화면(`/analysis`)은 KPI 7셀, 실적 막대 차트, 원문 재무제표 라인 표(보고서·구분 전환), 연도별 지표 표와 근거 공시 카드를 이 API로만 구성하고 가치지표·수급·공시 연결은 빈 상태로 두었으며, e2e 12건과 390·768·1360px·다크 실브라우저 QA를 통과했다. 이어 사용자가 승인한 가치지표 정정 계약에 따라 상장주식수를 KIS 시세 수집에서 함께 관측해 `reference.listed_share_count` 버전 사실로 저장하고(같은 값 재관측 멱등, 값 변경은 이력 보존 새 버전), 가치지표 `valuation` 블록을 구현했다. EPS는 공시 기본주당이익 원문을 그대로 쓰고(파생 EPS는 우선주 미반영 왜곡으로 계산하지 않음), PER = 현재가 ÷ 최근 연간 기본주당이익, 시가총액 = 현재가 × 보통주 상장주식수이며 응답은 가격·주식수·재무 기준을 항상 분리해 명시한다. 실수집으로 삼성전자 5,846,278,608주를 적재해 PER 41.56배·시가총액 1,604,803,477,896,000원을 수동 계산과 대조했고, KIS가 제공하는 per/pbr 외부 계산값은 노출하지 않는다. BPS·PBR은 우선주 반영 설계 확정 시 후속이다. 이어 사용자가 승인한 수급·공시 연결 계약에 따라 KIS 투자자별 매매(일별 개인·외국인·기관 순매수 수량·대금)를 서울 기준 당일을 제외한 버전 사실로 저장하고(실측 한계 기록: 세 주체 합 ≠ 0, 대금 백만원 단위, 최근 30거래일만 제공되어 수집 시점부터 축적), DART 공시 목록을 주요 유형별(정기 A·주요사항 B·지분 D·거래소 I)·접수번호 유일 불변 사실로 최근 1년 수집했다. 실수집으로 삼성전자·KODEX 200 수급 각 30거래일과 삼성전자 공시 2,837건을 적재했고 재수집은 멱등이며 KIS 원본 응답 값과 일치했다. 읽기 API 두 개와 기업 분석 D2(최근 8거래일 순매수 표)·D3(공시 목록과 DART 원문 링크) 카드를 구현해 4단계 화면 좌표(2b)가 전부 실제 값으로 채워졌다. 이어 사용자가 승인한 ETF 탐색 데이터 계약에 따라 KIS 공식 마스터 파일(비인증 고정폭 레코드)에서 KOSPI ETF 1,163종목을 버전 사실로 적재하고, ETF 현재가(FHPST02400000)의 원본 필드(NAV·괴리율 dprt·추적오차·추적배수·운용사·대표지수·순자산총액 억원)를 최신 스냅샷으로 전량 수집했다(개별 종목 실패는 기록 후 계속, 회당 약 21분). 분배율은 로드맵 수식(최근 12개월 분배금 합 ÷ 현재가 × 100)으로 분배금 이력 보유 ETF만 계산한다. 목록·상세 읽기 API와 승인 시안 3a의 ETF 탐색 화면(요약 KPI·순위표·투자자별 순매수·선택 상세)을 구현했고 순위는 등락률·거래량·괴리율·추적오차·순자산의 스냅샷 지표만 제공한다(거래대금·기간수익률·투자자별 순위는 후속). 이어 사용자가 승인한 백테스트·규칙형 전략 계약에 따라 6단계 1차를 구현했다. KIS 모의환경 기간별시세로 일봉을 2025-01-02부터 구간 분할 백필·재관측 확정해 종목당 394거래일을 확보했고, 삼성전자 2025년 배당 4건을 DART에서 소급 수집해 3건을 검증 락일로 확정했으며(2024년 기준일 1건은 달력 미커버로 계약대로 pending), `total_return` 수정주가 데이터셋을 전체 창으로 재발행했다. 결정적 백테스트 엔진은 T 마감 신호를 다음 거래 가능일 시가에 체결하고(주말·휴장 이월 확인), 안전 정책 §5 비용과 연도별 법정 매도세 버전(`research-krx-2025`·`2026`)을 적용하며, 검증 락일에 배당 현금을 반영하고, 모든 신호를 접두 시계열 재계산으로 검사해 미래정보 참조를 거부한다. 이동평균·RSI 전략 실행 2건(삼성전자 +44.35%, KODEX 200 +10.60%, 벤치마크 +254.49%는 원본 시세 그대로)의 재현성과 신호 107건 독립 재계산 일치를 검증했고, 실행 기록은 `strategy` 스키마에 저장되어 `/api/backtests`로 조회된다. 이어 사용자가 승인한 ADR-0007에 따라 7단계의 주문 제출 이전 계층을 구현했다. 거래 안전 정책 §3·§4의 한도 16종을 순수 함수 위험검사로 표현하고(경계값 아래·같음·초과 테스트 고정), 매수 신호는 종목 한도 10%를 목표 비중으로 주문 1건 5%씩 분할하며, 기준가는 계획 시점에 새로 조회한 현재가만 사용해 10초 규칙을 만족시킨다. 계좌번호는 해시 참조만 저장하고, 주문은 결정적 `client_order_id` UNIQUE로 중복이 구조적으로 차단된다. 자동매매 상태 머신은 정책 §6 그래프와 거래일 변경 시 `DISABLED` 복귀를 구현했다. 실환경에서 비활성 상태 차단 계획 저장, 상태 전이 5건, 계좌 secret 미설정 시 `api_failure` 기록 후 중단, 실HTTP 조회를 확인했고 검증 후 자동매매를 `disabled`로 되돌렸다. 업종 분류 원천이 없어 총 노출 실질 상한이 NAV 10%가 되는 것은 정책 그대로의 보수적 결과로 기록했다. 같은 날 승인 시안 2c의 전략 연구 화면을 구현해 저장된 실행 기록·체결·NAV 곡선·입력 계보가 전부 실제 API 값으로 표시되고, D 좌표는 사용자 승인으로 신호·체결 기록을 표시하며 목표 포지션 변환은 7단계에서 확장한다. 종합 순위·ETF 모멘텀 전략(유니버스 확장)은 후속이며, KIS 수정주가 대조는 분할 이력 종목 확보 시 수행한다. 이어 실계좌 잔고 조회를 검증하고(모의계좌 NAV 10,000,000원 = 증권사 `nass_amt`, 저장 원본·응답에 계좌번호 없음, 해시 참조 `4aec6939a6d3`만) 계좌 secret 자릿수 검사와 원화 금액 정규화를 추가했다. 2026-08-18에는 승인 시안 4a의 모의매매 콘솔 화면(`/trading`)을 구현했다. 사용자 결정 네 가지를 반영해 (1) 제어 버튼 없이 자동매매 상태 표시와 worker CLI 안내만 두고(ADR-0007 결정 1 유지), (2) 위험 한도 소진율은 새 읽기 API `GET /api/trading/risk-limits`가 정책 §3 한도 13종의 한도값·현재값·소진율과 §4 주문 가능 조건을 제공하며(소진율은 저장하지 않고 순수 함수로 계산, 값이 없으면 `MISSING_SNAPSHOT`·`MISSING_SECTOR_DATA` 등 사유 코드), (3) 주문 내역의 체결 열은 제출 단계가 없어 값을 만들지 않고 줄표로 두며, (4) 모바일 탭바는 운영·시장·기업·ETF·전략·매매 6개로 확장했다. 주문 카운터 SQL은 쓰기 저장소와 읽기 어댑터가 공유 모듈을 쓰고, `GET /api/trading/orders`가 계획 경계를 넘는 주문 목록을 제공한다. 실제 모의계좌 데이터와 빈 데이터베이스(CI 동등) 두 상태에서 라이트·다크 × 390/768/1360px 실브라우저 QA(콘솔 오류 0·오버플로 없음·계좌번호 비노출)와 e2e 24건 두 모드를 통과했다. 주문·포지션 표의 실데이터 대조는 다음 거래일 장중 계획 생성 뒤에 수행한다. 이어 사용자가 승인한 ADR-0008에 따라 주문 제출 계층을 구현했다. 결정 네 가지는 (1) 첫 슬라이스는 worker CLI 수동 제출만(HTTP 쓰기 경로 없음), (2) 체결·상태 동기화는 일별주문체결조회 폴링, (3) 설명할 수 없는 증권사 대조 불일치는 자동 정리하지 않고 `ACCOUNT_NOT_RECONCILED`로 자동매매를 일시정지, (4) 비상정지는 정책 §6대로 미체결 취소를 시도하고 보유는 청산하지 않는다. 실측으로 모의환경 제약을 확인해 설계에 반영했다: 일별주문체결조회(`VTTC8001R`)는 동작하지만 정정취소가능주문조회(`VTTC8036R`)는 모의 미지원(`msg_cd=90000000`)이라 미체결 판정을 `reconcile_problem` 이벤트 유형을 추가했다. 장 마감 시간이라 주문을 보내지 않는 경로만 실환경 검증했다: 비활성 상태 제출 차단, 22:04 KST의 `MARKET_CLOSED` 차단(외부 호출 없음), 실제 일별주문체결 조회(원본 저장·계좌번호 비노출 확인), 비상정지 전이와 취소 대상 0건. 실제 주문 전송·체결·취소 검증은 다음 거래일 장중에 수행하며 절차는 QA 문서에 있다. 2026-08-19 09:06~09:30 KST에 사용자 승인으로 실제 모의주문 장중 검증을 수행했다. 삼성전자 2주씩 2건(지정가 250,000원, 종목 한도 10% 정확히)을 제출해 `rt_cd=0`·`msg_cd=40600000`과 주문번호 `0000008637`·`0000008645`·지점번호 `00950`·주문시각을 저장했고, 제출 응답 계약이 실데이터로 검증됐다. 재실행은 `submitted=0`으로 멱등이며, 두 주문은 즉시 전량 체결돼 잔고에 삼성전자 4주(평균 248,750원)가 잡혔다. 잔고 `output1` 보유 종목 필드도 실데이터로 확인해 fixture로 승격했다(대기 항목 해소). 검증에서 결함 3건을 발견해 고쳤다: (1) 예상 노출에 이전 계획의 미체결·계획 주문이 빠져 미분류 합계가 NAV의 19.2%까지 계획된 정책 §2 위반 — `PendingExposure` 입력을 추가하고 잘못된 계획은 새 `--withdraw`로 철회했다, (2) NAV를 예수금 총액으로 계산해 미결제 매수분을 이중 계산한 정책 §2 위반 — 가수도정산금액 기준으로 고쳐 증권사 순자산금액과 정확히 일치시키고 불일치 시 `ACCOUNT_NOT_RECONCILED` 차단 가드를 넣었다, (3) 최소 현금 비중도 같은 이유로 100.05%로 보고되던 것을 정산 기준(`AccountState.settled_cash`)으로 고쳤다. 미해결 한 가지는 모의환경 일별주문체결조회가 장중에 `output1`을 빈 배열로 반환해(6가지 파라미터 조합 모두 동일) 주문별 체결을 확정할 수 없는 것이다. 내부 주문은 `SUBMITTED`로 남고 미체결 존재로 이후 계획이 차단된다(fail-closed 정상 동작). 장 마감 후 재확인이 필요하며, 채워지지 않으면 실시간 체결통보(웹소켓 `H0STCNI9`) 도입과 집계 기반 확정 규칙 중 하나를 사용자가 결정해야 한다. 부분체결 전이와 취소 성공 경로는 오늘 즉시 전량 체결로 관측하지 못해 다음 실주문에서 지정가를 벌려 확인한다. 다음 기술 작업은 이 결정과 자동 스케줄 제출·주문 정정이다. 기본 Compose와 모의환경은 계속 KIS 자동 확인이 꺼져 있고 실전 달력 전용 worker만 자격증명을 받는다. 사용자는 별도로 KIS 화면의 값과 거래일을 최종 육안 대조한다. 승인 디자인 구현 세션에서는 공통 프리미티브와 대상 화면이 390px, 768px, 1360px 실제 브라우저 QA를 통과해야 한다.
