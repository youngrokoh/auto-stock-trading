# ADR-0014: 주문·위험 이벤트 외부 알림 경계

- 상태: 승인
- 결정일: 2026-08-24
- 승인: 2026-08-24 사용자 승인. 방향(외부 메신저)과 네 가지 설계 선택(Telegram 봇 / 주문 내용까지·계좌·NAV 제외 / 전송 실패는 매매를 막지 않는다 / 아웃박스 + 폴러)을 먼저 받고, 초안의 승인 질문 네 개에 답을 받았다 — ① 공개 범위 확정, ② 요약 대체 도입, ③ 알림 대상은 **심각도 선별**, ④ 봇 토큰은 나중에 넣고 구현·테스트를 먼저 진행(실측은 대기)
- 관련 결정: [ADR-0009 실시간 체결통보 수신 경계](0009-realtime-fill-notification.md), [ADR-0008 모의투자 주문 제출·체결 동기화 경계](0008-paper-order-submission.md), [ADR-0007 모의투자 주문 계획과 위험검사 경계](0007-paper-order-planning-and-risk.md), [ADR-0005 KIS 토큰·요청 조정](0005-kis-token-and-rate-coordination.md)
- 관련 정책: [거래 안전 정책](../spec/trading-safety-policy.md), [모의투자·실전투자 전환 게이트](../spec/paper-to-live-gate.md)

## 배경

로드맵 7단계의 구현 항목 중 "주문과 위험 이벤트를 웹 또는 메신저로 알린다"만 남았다. 사용자가
2026-08-24에 **외부 메신저**를 선택했다.

### 지금 있는 것

알릴 사실은 이미 전부 저장돼 있다. 새로 만들 사실은 없고 **내보내기만** 없다.

| 원천 | 실제 기록 수 (2026-08-24) | 내용 |
|---|---:|---|
| `trading.automation_event` | 127 | `state_change` 67, `listener_state` 30, `reconcile_problem` 27, `attestation` 2, `api_failure` 1 |
| `trading.order_event` | 약 85 | 상태 전이와 사유 코드(증권사 `40600000`·`40590000`, `FILL_NOTIFICATION`, `cancel_requested` 등) |
| `trading.risk_decision` | — | 주문별 규칙 통과·거절 판정 |
| `trading.fill_notification` | — | 마스킹된 체결통보 원본 |

### 이 결정이 새로 만드는 경계

기존 외부 어댑터(KIS·DART·KODEX·KRX)는 **모두 가져오기**다. 메신저는 이 시스템에서 **처음으로 밖으로
내보내는 경로**이며, 그래서 지금까지 없던 두 가지 질문이 생긴다.

1. 무엇이 제3자 서버에 도달해도 되는가. 자격증명·계좌번호는 이미 금지돼 있지만, 종목·수량·가격·NAV는
   기존 규칙이 다루지 않는다 — 나가는 경로가 없었기 때문이다.
2. 전송 실패가 매매에 어떤 영향을 주는가. 리스너는 "붙어 있지 않으면 제출 금지"인데(ADR-0009 결정 3),
   같은 논리를 알림에도 적용하면 제3자 장애가 우리 매매를 정지시킨다.

## 원천 확인 (2026-08-24, Telegram 공식 문서)

| 사실 | 값 | 출처 |
|---|---|---|
| 전송 | `POST https://api.telegram.org/bot<token>/sendMessage`, 본문 `chat_id`·`text` | Bot API |
| 오류 형식 | JSON `ok`(bool)·`description`(string)·`error_code`(int)·선택 `parameters`(`ResponseParameters`) | Bot API |
| `chat_id` | `Chat.id`, "at most 52 significant bits" — 64비트 정수로 다룬다 | Bot API |
| 단일 대화 한도 | "avoid sending more than one message per second" | Bot FAQ |
| 그룹 한도 | "bots are not be able to send more than 20 messages per minute" | Bot FAQ |
| 전체 한도 | "bots are not able to broadcast more than about 30 messages per second" | Bot FAQ |
| 초과 시 | 429 | Bot FAQ |

**미실측.** 봇 토큰이 아직 없어 실제 호출을 하지 못했다. 위 표는 **문서 기준**이며, 토큰이 준비되면
DART 키·계좌 비밀과 같은 방식으로 실측해 계약에 기록한다. 특히 다음은 문서만으로 단정하지 않는다.

- 429 응답이 `parameters.retry_after`를 항상 싣는지
- `text` 길이 상한(문서상 4096자로 알려져 있으나 이번 조회에서 해당 절을 확인하지 못했다)
- 실패 시 재시도가 중복 메시지를 만드는지

## 결정

### 1. 알림은 이미 저장된 사실의 사본이다 — 새 사실을 만들지 않는다

메신저로 나가는 모든 값은 `trading` 스키마에 이미 있는 행에서 파생한다. 알림 경로가 시세를 조회하거나
계좌를 다시 읽는 일은 없다. 알림이 틀렸다면 원천이 틀린 것이고, 알림만 고치는 수정은 하지 않는다.

### 2. 전송은 아웃박스 + 폴러다 — 매매 트랜잭션에 외부 호출을 넣지 않는다

**아웃박스 행은 폴러가 만든다**(투영). 이벤트 쓰기 경로는 손대지 않는다.

초안은 "이벤트를 쓸 때 같은 트랜잭션에서" 아웃박스 행을 만드는 고전적 transactional outbox를 적었다.
구현 직전에 바꿨다. 그러려면 주문·자동매매·위험판정의 모든 쓰기 경로(`transition_order`,
`transition_automation`, `record_order_event`, `record_reconcile_problem`, `record_api_failure`,
`save_plan`)에 선별 규칙을 넣어야 한다. **주문 쓰기 경로를 알림 때문에 고치는 것은 위험 대비 이득이
없고**(`trading_store.py`는 이미 리뷰 임계 LOC를 넘겼다), 선별 규칙이 여섯 곳으로 흩어진다.

대신 폴러가 **아직 아웃박스 행이 없는 이벤트**를 anti-join으로 찾아 투영한다. 원자성 대신
`(environment, source, source_id)` 유일 제약으로 중복을 막는다. 시각 커서를 쓰지 않으므로 커밋 순서가
뒤바뀐 이벤트도 놓치지 않는다.

첫 실행은 **당일 이벤트만** 투영하고 워터마크를 기록한다. 워터마크 없이 anti-join만 돌리면 과거 전체가
한꺼번에 대상이 된다. 이후에는 워터마크 이후 미투영 이벤트를 모두 투영하므로, 알림 프로세스가 멈춰
있었던 동안의 이벤트도 다시 켜면 밀린 채로 전달된다(한도는 결정 7의 상한·요약이 처리한다).

폴러가 미발신 행을 읽어 보낸다.

- 주문 쓰기 경로는 외부 HTTP에 묶이지 않는다. Telegram 지연이 주문 커밋을 늦추지 않는다.
- 프로세스가 죽어도 미발신 행이 남으므로 알림이 사라지지 않는다.
- 재시도·중복제거·실패 이력이 **사실로 남는다**. "보냈다고 생각했는데 안 갔다"를 구분할 수 있다.

이벤트 지점 직송은 채택하지 않는다. 전송 실패가 곧 소실이고, 장애가 주문 경로로 전파된다.

### 3. 나가는 범위: 주문 내용까지, 계좌·NAV는 제외

보내는 것: 종목코드·종목명·매매구분·수량·지정가·주문 상태·사유 코드·이벤트 시각·증권사 주문번호.

보내지 않는 것: **계좌번호와 그 해시 참조, NAV, 현금 잔고, 보유 전체, 노출 비율, 자격증명, 원본 응답.**

근거: 알림이 쓸모가 있으려면 "무엇이 얼마"가 필요하다. 반면 자산 규모는 알림의 목적에 필요하지 않고,
제3자 서버에 도달하면 되돌릴 수 없다. 계좌번호는 시스템 어디에도 평문으로 없으므로(해시 참조만) 이
규칙은 해시 참조까지 금지해 계좌 식별 가능성을 없앤다.

위험 관련 알림은 **한도 위반 사실과 규칙 코드**를 보내고 분모(NAV)와 비율은 보내지 않는다. 예:
"주문 거절 · RISK_SYMBOL_EXPOSURE" — 얼마나 초과했는지는 콘솔에서 본다.

### 3-1. 알림 대상은 심각도로 선별한다

사람이 **행동할 수 있는** 이벤트만 보낸다.

| 보냄 | 제외 |
|---|---|
| 주문 상태 전이(`order_event`의 상태 변경) | `listener_state`(부착·해제 반복) |
| 위험 거절(`risk_decision`의 차단 판정) | 상태가 바뀌지 않는 정보성 주문 이벤트 |
| `reconcile_problem` | 통과한 위험 판정 |
| 자동매매 상태 변경(`state_change`) | |
| `api_failure` | |
| `attestation` | |

근거는 실제 기록이다: `automation_event` 127건 중 30건이 `listener_state`다. 사람이 할 일이 없는
알림이 섞이면 진짜 알림을 놓치고, 초당 1건 한도를 불필요하게 쓴다.

### 4. 전송 실패는 매매를 막지 않는다

알림은 이미 생산된 사실의 사본이므로 제출 전제조건으로 삼지 않는다. 메신저 장애가 사람이 위험을 줄이는
수단을 마비시키면 안 된다 — 부분 취소에 리스너 조건을 면제한 것과 같은 논리다(ADR-0013 결정 3).

대신 **침묵하지 않는다**: 실패를 아웃박스 행에 기록하고, 미발신·실패 건수를 조회 API와 콘솔에 드러낸다.
"알림이 조용한 것"과 "보낼 것이 없는 것"이 화면에서 구분돼야 한다.

리스너와의 차이는 의도적이다. 리스너는 장중 체결의 **유일한** 진실 원천이므로 없으면 주문을 만들 수
없다. 알림은 저장된 사실의 중복이므로 없어도 진실이 유실되지 않는다.

### 5. 자격증명은 Docker secret 파일로만 들어온다

봇 토큰과 `chat_id` 둘 다 secret이다. `chat_id`는 인증 값이 아니지만 대상 식별자이므로 저장소·문서·로그에
남기지 않는다(잘못 커밋되면 알림이 남의 대화로 갈 수 있다).

- `AUTO_STOCK_TELEGRAM_BOT_TOKEN_FILE`, `AUTO_STOCK_TELEGRAM_CHAT_ID_FILE`
- 로그에는 HTTP 메서드·상태·소요시간만 남기고 URL을 남기지 않는다 — **토큰이 URL 경로에 들어간다.**
  기존 KIS 어댑터가 헤더를 로그에서 제외하는 것과 같은 이유이며, 여기서는 경로 자체가 비밀이다.

### 6. 알림 프로세스는 기본 구성에서 꺼져 있다

리스너와 같은 방식으로 opt-in Compose 오버라이드(`infra/compose.notifications.yaml`)로만 켠다. 자격증명이
없는 환경에서 기본 스택이 실패하지 않아야 하고, 알림은 매매의 전제가 아니므로 기본값은 꺼짐이다.

### 7. 한도는 문서 값을 그대로 지킨다 — 초당 1건, 재시도는 백오프

단일 대화 초당 1건을 상한으로 잡고 폴러가 직렬로 보낸다. 429는 실패로 기록하고 백오프 후 재시도하며,
`parameters.retry_after`가 오면 그 값을 따른다(오지 않을 수 있으므로 기본 백오프를 함께 둔다).

한 번의 폴에서 보낼 건수에 상한을 두고, 상한을 넘으면 **개별 알림 대신 요약 한 건**을 보낸다. 200개
주문이 한 번에 처리될 때 200개 메시지를 보내면 한도에 걸리고 사람도 읽지 못한다. 잘라낸 건수를 명시한다.

### 8. 실패한 알림을 조용히 지우지 않는다

일정 횟수 재시도 후에도 실패하면 `failed`로 남기고 자동 삭제하지 않는다. 사람이 콘솔에서 보고 판단한다.
"보내지 못한 알림이 있다"는 사실이 사라지면 사후 감사가 불가능하다.

## 결과

승인되면:

- 주문·위험 이벤트가 사람이 화면을 보고 있지 않아도 도달한다. 장중 감시 부담이 줄어든다.
- 알림 전송 이력이 감사 대상이 된다(무엇을 언제 어디로 보냈는가).
- 제3자 서버에 종목·수량·가격이 도달한다. 이것이 이 결정의 실질적 비용이며, 계좌 규모는 여전히 나가지 않는다.

승인되지 않으면:

- 알림은 화면 안에서만 가능하다(콘솔 폴링). 장을 보고 있지 않으면 체결·거절·차단을 즉시 알 수 없다.

## 대안

- **화면 안 알림만**: 나가는 경로가 없어 유출 면적이 0이다. 그러나 사람이 화면을 봐야 알 수 있어
  "장중 감시 부담을 줄인다"는 목적을 달성하지 못한다.
- **이메일(SMTP)**: 메신저보다 익숙하지만 전송 지연이 크고 스팸 처리로 유실될 수 있다. 즉시성이 목적인
  알림에 맞지 않는다.
- **KakaoTalk**: 국내 사용자에게 자연스럽지만 "나에게 보내기"가 사용자별 OAuth를 요구하고 알림톡은
  사업자 심사가 필요하다. 개인 프로젝트의 자격증명 모델과 맞지 않는다.
- **계좌 요약까지 포함**: 한 번에 상황 판단이 된다. 그러나 자산 규모가 제3자 서버에 남고, 알림의
  목적(무엇이 일어났는가)에는 필요하지 않다.
- **전송 실패 시 매매 차단**: 일관돼 보인다. 그러나 제3자 장애가 우리 매매를 정지시키고, 위험을 줄이는
  행동까지 막는다.

## 재검토 조건

- 실측에서 429 동작이나 길이 상한이 문서와 다르면 계약을 고친다.
- 실전 전환 게이트를 통과하면 공개 범위를 다시 검토한다. 실전에서는 같은 정보의 민감도가 올라간다.
- 알림 대상이 늘어 한도에 상시로 걸리면 배치·요약 정책을 다시 정한다.
