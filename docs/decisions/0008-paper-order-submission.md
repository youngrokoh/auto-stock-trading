# ADR-0008: 모의투자 주문 제출·체결 동기화 경계

- 상태: 승인
- 결정일: 2026-08-18
- 승인: 사용자가 2026-08-18에 네 가지 결정을 승인 — ① 첫 슬라이스는 worker CLI 수동 제출만, ② 체결·상태 동기화는 일별주문체결조회 폴링, ③ 증권사 대조 불일치는 차단하고 사람이 확인, ④ 비상정지는 정책대로 미체결 자동 취소를 시도

## 배경

ADR-0007은 `PLANNED` 주문까지만 만들고 증권사 쓰기 API를 호출하지 않기로 결정했다. 이 단계는
그 결정의 다음 절반, 즉 **증권사에 실제로 주문을 보내는 첫 코드**다. 손실로 직결되는 경로이므로
자동화 범위와 실패 처리 경계를 코드보다 먼저 고정한다.

실측으로 확인한 모의환경 제약 두 가지가 설계를 규정한다(2026-08-18 읽기 전용 확인).

- 일별주문체결조회(`VTTC8001R`)는 동작한다. 내역이 없으면 `rt_cd=0`, `msg_cd=70070000`,
  `output1`은 빈 배열이고 `output2`가 주문·체결 합계를 준다.
- 정정취소가능주문조회(`VTTC8036R`)는 **모의투자 미지원**이다(`rt_cd=1`, `msg_cd=90000000`,
  "모의투자에서는 해당업무가 제공되지 않습니다"). 따라서 미체결 목록을 이 TR로 얻을 수 없다.

## 결정

### 1. 주문 제출은 worker CLI 수동 실행만 제공한다

첫 슬라이스는 사람이 계획 ID를 지정해 명령을 실행할 때만 증권사에 주문을 보낸다. HTTP 쓰기
엔드포인트를 만들지 않고(ADR-0007 결정 1의 경계 유지), Taskiq 예약 자동 제출도 만들지 않는다.
제출 입력은 위험검사를 통과해 저장된 `PLANNED` 주문뿐이며, 제출 시점에 자동매매 상태가 `RUNNING`
이고 주문 허용시간·거래일 조건을 다시 검사한다. 주기적 자동 제출은 이 슬라이스 검증 후 별도
승인으로 추가한다.

### 2. 체결·상태 동기화는 일별주문체결조회 폴링으로 한다

제출 직후와 명시적 동기화 명령에서 `VTTC8001R`을 조회해 체결 수량, 잔여 수량, 취소·거절 여부를
내부 주문 상태에 반영한다. 실시간 체결통보 웹소켓은 상시 프로세스·재연결·순서 보장·유실 재동기화
설계가 필요하므로 이 슬라이스에서 채택하지 않는다. 조회 원본은 append-only로 보존하고 상태 전이는
`trading.order_event`에 사유와 함께 남긴다.

### 3. 설명할 수 없는 불일치는 차단하고 사람이 확인한다

증권사 응답은 체결 사실의 근거이므로 체결 수량·평균단가·취소 여부는 그대로 반영한다. 그러나
내부에 없는 증권사 주문, 내부 수량을 초과하는 체결처럼 설명할 수 없는 불일치를 발견하면 자동으로
정리하지 않는다. 불일치를 사유와 함께 기록하고 자동매매를 `PAUSED`로 전이해 신규 주문을 차단하며,
사람이 확인한 뒤에만 재개한다. 정책 §7.2의 `ACCOUNT_NOT_RECONCILED`가 이 상태의 코드다.

### 4. 비상정지는 미체결 주문 취소를 시도하고 보유는 건드리지 않는다

`EMERGENCY_STOP` 전이 시 내부에 제출 이후 상태로 남은 주문의 취소를 정책 §6대로 시도한다. 취소
결과는 주문별로 이벤트에 남기고, 취소에 실패한 주문이 있으면 차단 상태를 유지한다. 보유 종목의
자동 시장가 청산은 정책 §6이 금지하므로 구현하지 않는다.

### 5. 중복 제출은 상태 전이와 식별자로 이중 차단한다

제출은 `PLANNED` 상태의 주문만 대상으로 하고, 제출 성공 시 같은 트랜잭션에서 `SUBMITTED`로
전이한다. 이미 `SUBMITTED` 이후 상태인 주문은 제출 대상에서 제외되므로 같은 명령을 두 번 실행해도
증권사에 두 번 보내지 않는다. `client_order_id` UNIQUE 제약은 계획 단계의 중복을, 상태 전이는
제출 단계의 중복을 막는다. 증권사 주문번호(`ODNO`)와 지점번호(`KRX_FWDG_ORD_ORGNO`)는 주문 행에
저장해 정정·취소·대조의 기준으로 쓴다.

### 6. 제출 실패와 응답 이상은 fail-closed다

`rt_cd`가 `0`이 아니면 주문을 `REJECTED`로 기록하고 증권사 메시지 코드를 사유로 남긴다. 응답
파싱이 실패하거나 주문번호가 없으면 상태를 추측하지 않고 실패로 남긴 뒤 동기화 명령이 증권사
사실로 상태를 확정하게 한다. 연속 실패는 정책 §3의 `RISK_API_FAILURES` 규칙으로 자동매매를
일시정지한다.

### 7. 모의 자격증명만 사용하고 계좌번호는 해시 참조만 남긴다

ADR-0007 결정 5를 그대로 유지한다. 주문·취소·체결 조회 경로에는 모의 자격증명만 주입하고,
CLI는 실전 환경에서 실행을 거부한다. 요청 지문·저장 원본·API 응답·로그에는 계좌번호 원문이 아닌
12자 해시 참조만 남긴다.

## 결과

- 사람이 실행할 때만 주문이 나가므로 첫 write 경로의 폭발 반경이 명령 한 번으로 제한된다.
- 미체결 목록 TR이 없는 모의환경에서도 일별주문체결조회 하나로 체결·잔여·취소를 판정할 수 있다.
- 불일치가 조용히 정리되지 않으므로 원인 추적이 가능하고, 정책의 차단 코드가 실제로 발생한다.
- 실시간 체결 반영과 자동 제출 스케줄은 후속 결정으로 남는다.

## 대안

- **웹소켓 체결통보 우선 도입**: 지연이 작지만 상시 프로세스와 유실 복구 설계가 먼저 필요하다.
  폴링으로 사실을 확정하는 경로가 있어야 웹소켓 유실을 검증할 수 있으므로 순서를 뒤로 둔다.
- **증권사 상태 자동 덮어쓰기**: 자동매매를 멈추지 않아 운영이 매끄럽지만, 이중 주문 같은 원인을
  숨긴다. 손실 방지를 우선하는 정책과 맞지 않는다.
- **HTTP 제어 엔드포인트로 제출**: 화면에서 즉시 제출할 수 있지만 인증·권한 설계가 없는 현재
  상태에서 주문 경로를 웹에 노출하게 된다. ADR-0007 결정 1의 경계를 유지한다.
