# 실시간 체결통보 계약

- 상태: 구현 기준
- 작성일: 2026-08-19
- 승인: 사용자가 2026-08-19에 [ADR-0009](../decisions/0009-realtime-fill-notification.md)의 네 가지 결정을 승인
- 관련 결정: [ADR-0009](../decisions/0009-realtime-fill-notification.md), [ADR-0008](../decisions/0008-paper-order-submission.md), [ADR-0007](../decisions/0007-paper-order-planning-and-risk.md), [ADR-0005](../decisions/0005-kis-token-and-rate-coordination.md)
- 관련 정책: [거래 안전 정책](../spec/trading-safety-policy.md), [모의투자·실전투자 전환 게이트](../spec/paper-to-live-gate.md)
- 관련 계약: [주문 제출·체결 동기화 계약](order-submission-contract.md), [주문 계획·위험검사 데이터 계약](order-planning-risk-contract.md)
- 관련 API: [모의투자 주문 계획 읽기 API](../api/trading-api.md)

## 목적

KIS 모의환경의 실시간 체결통보(`H0STCNI9`)를 수신해 장중에 주문별 체결을 확정하는 경로의 정의를
고정한다. 실전 환경(`H0STCNI0`)은 이 계약의 범위가 아니며 전환 게이트를 따른다.

이 경로가 필요한 이유는 일별주문체결조회가 장중에 주문별 행을 주지 않기 때문이다
([주문 제출·체결 동기화 계약](order-submission-contract.md)의 실측 한계 참조).

## 원칙

1. **리스너는 읽기 전용이다.** 통보 수신은 주문을 제출·정정·취소하지 않는다. 웹소켓으로 들어온
   값이 주문 실행을 촉발하는 경로는 없다.
2. **통보는 증권사 사실이다.** 체결 수량·체결가는 통보 값으로만 갱신하고 내부에서 추정하지 않는다.
3. **누적은 수신한 프레임의 합이다.** 통보는 누적 체결 수량을 주지 않으므로 프레임을 더해 만들고,
   같은 프레임을 두 번 반영하지 않는다.
4. **놓친 구간은 이어붙이지 않는다.** 리스너가 붙기 전 또는 단절 구간의 체결은 추정하지 않고
   차단으로 처리한다.
5. **개인정보는 저장 전에 지운다.** 복호화 본문의 고객ID·계좌번호·계좌명은 마스킹 후 저장한다.
   이는 주문 제출·체결 동기화 계약 원칙 4(원본 보존)의 명시적 예외다.
6. **자격증명은 파일과 캐시에만 있다.** 접속키·HTS ID·계좌번호는 로그·진단·API 응답에 넣지 않는다.

## 접속

| 항목 | 값 |
|---|---|
| 모의 웹소켓 | `ws://ops.koreainvestment.com:31000` |
| 실전 웹소켓 | `ws://ops.koreainvestment.com:21000` (이 계약 범위 밖) |
| 모의 TR | `H0STCNI9` |
| `tr_key` | 모의투자 HTS ID. Docker secret으로만 주입한다 |
| 접속키 발급 | `POST /oauth2/Approval`, 본문 `grant_type`=`client_credentials`, `appkey`, `secretkey` |

접속키 발급 본문의 비밀 필드명은 **`secretkey`**다. 접근토큰 발급(`/oauth2/tokenP`)의 `appsecret`과
다르므로 재사용하지 않는다. 응답은 `approval_key` 하나이며 만료 시각을 주지 않는다. 따라서 만료는
우리 쪽 보수적 TTL로만 관리하고(ADR-0005 방식으로 Valkey에 캐시), 구독이 거부되면 캐시를 버리고
재발급한다. Valkey 장애 시 자체 키를 발급해 우회하지 않는다.

`ping_interval`은 끈다. 연결 유지는 서버가 보내는 `PINGPONG` 제어 프레임에 같은 프레임으로 응답해
수행한다.

### 구독 프레임

```json
{
  "header": {
    "approval_key": "<approval_key>",
    "custtype": "P",
    "tr_type": "1",
    "content-type": "utf-8"
  },
  "body": { "input": { "tr_id": "H0STCNI9", "tr_key": "<HTS ID>" } }
}
```

`tr_type`은 `1`이 등록, `2`가 해제다. 종료 시 해제 프레임을 보내고 연결을 닫는다.

## 프레임 판별

수신 프레임은 두 종류이며 첫 글자로 갈린다.

| 형태 | 판별 | 처리 |
|---|---|---|
| 제어 메시지 | `{`로 시작하는 JSON | `tr_id`가 `PINGPONG`이면 같은 프레임으로 응답. 구독 응답이면 `rt_cd`·`msg_cd`를 검사하고 `output.key`·`output.iv`를 보관 |
| 데이터 | `0`/`1` + `|` 구분 4토큰 | `암호화유무|TR ID|데이터건수|응답데이터` |

체결통보는 항상 암호화되어 오므로 데이터 프레임의 암호화유무는 `1`이다. `0`(평문)으로 오면 계약
위반으로 보고 fail-closed 처리한다. TR ID가 구독한 값과 다르면 처리하지 않고 문제로 기록한다.

구독 성공 응답이 `output.key`·`output.iv`를 주기 전에 도착한 데이터 프레임은 복호화할 수 없으므로
버리지 않고 문제로 기록한다(체결을 놓쳤을 수 있으므로 차단 대상이다).

## 복호화

| 항목 | 값 |
|---|---|
| 알고리즘 | AES-256-CBC |
| 키 | 구독 성공 응답 `output.key`의 UTF-8 바이트(32바이트) |
| IV | 구독 성공 응답 `output.iv`의 UTF-8 바이트(16바이트) |
| 입력 | 응답데이터 토큰을 base64 디코딩한 바이트 |
| 패딩 | PKCS#7 제거 |
| 출력 | UTF-8 문자열 |

복호화 실패, 패딩 이상, UTF-8 디코딩 실패는 모두 fail-closed다. 원문 바이트나 키·IV를 로그에
남기지 않는다.

## 본문 필드

복호화 결과는 `^`로 구분된 23개 필드다. 데이터건수가 2 이상이면 필드 수는 23의 배수여야 하며,
배수가 아니면 계약 위반으로 fail-closed 처리한다.

| # | 이름 | 코드 | 사용 | 저장 |
|---|---|---|---|---|
| 0 | 고객ID | `CUST_ID` | 사용하지 않음 | **마스킹** |
| 1 | 계좌번호 | `ACNT_NO` | 사용하지 않음 | **마스킹** |
| 2 | 주문번호 | `ODER_NO` | 내부 주문 대조 키 | 저장 |
| 3 | 원주문번호 | `OODER_NO` | 정정·취소 원주문 추적 | 저장 |
| 4 | 매도매수구분 | `SELN_BYOV_CLS` | `01` 매도 / `02` 매수 | 저장 |
| 5 | 정정구분 | `RCTF_CLS` | 정정·취소 판별 보조 | 저장 |
| 6 | 주문종류 | `ODER_KIND` | 기록 | 저장 |
| 7 | 주문조건 | `ODER_COND` | 기록 | 저장 |
| 8 | 주식단축종목코드 | `STCK_SHRN_ISCD` | 종목 일치 검사 | 저장 |
| 9 | 체결수량 | `CNTG_QTY` | 체결 누적 가산분 | 저장 |
| 10 | 체결단가 | `CNTG_UNPR` | 평균 체결가 계산 | 저장 |
| 11 | 주식체결시간 | `STCK_CNTG_HOUR` | 증권사 시각 원문(HHMMSS) | 저장 |
| 12 | 거부여부 | `RFUS_YN` | `0` 정상 / `1` 거부 | 저장 |
| 13 | 체결여부 | `CNTG_YN` | `1` 주문·정정·취소·거부 / `2` 체결 | 저장 |
| 14 | 접수여부 | `ACPT_YN` | `1` 주문접수 / `2` 확인 / `3` 취소 | 저장 |
| 15 | 지점번호 | `BRNC_NO` | 기록 | 저장 |
| 16 | 주문수량 | `ODER_QTY` | 주문 수량 대조 | 저장 |
| 17 | 계좌명 | `ACNT_NAME` | 사용하지 않음 | **마스킹** |
| 18 | **미확인** (문서상 체결종목명) | — | 사용하지 않음 | 저장하지 않음 |
| 19 | **미확인** (문서상 신용구분) | — | 사용하지 않음 | 저장하지 않음 |
| 20 | **미확인** (문서상 신용대출일자) | — | 사용하지 않음 | 저장하지 않음 |
| 21 | 체결종목명 | `CNTG_ISNM40` | 사용하지 않음 | 저장하지 않음 |
| 22 | 주문가격 | `ODER_PRC` | 사용하지 않음 | 저장하지 않음 |

인덱스 0~17과 22의 이름·의미는 2026-08-19 실제 통보로 대조했다. 판정에 쓰는 필드
(주문번호·매도매수구분·종목코드·체결수량·체결단가·거부여부·체결여부·접수여부·주문수량)는 모두
일치한다.

인덱스 18~20은 문서의 이름(체결종목명·신용구분·신용대출일자)과 실측값이 맞지 않는다. 실측에서는
`1Y`·`10`·공백이었고 종목명은 인덱스 21에 있었다. 이 세 자리는 어떤 판정에도 쓰지 않으므로 이름을
추정하지 않고 미확인으로 남긴다. 값이 필요해지면 그때 KIS에 확인해 계약을 고친다.

측정으로 확인한 값 규칙(추정하지 않는다):

- **체결단가(10)는 통보 종류에 따라 다른 값이다.** 주문 통보(`CNTG_YN=1`)에서는 주문 지정가,
  체결 통보(`CNTG_YN=2`)에서는 실제 체결가다. 그래서 평균 체결가는 체결 통보에서만 계산한다.
- 주문가격(22)은 주문 통보에서 공백이고 체결 통보에서 지정가를 담는다.
- 원주문번호(3)는 신규 주문에서 공백이다.
- 주문 통보와 체결 통보가 같은 초에 발생하면 체결시각(11)이 같다.

### 마스킹

저장 전에 인덱스 0·1·17을 고정 문자열 `***`로 치환한다. 마스킹은 필드 분해 후 재조립으로 하며,
치환 전 문자열을 어디에도 남기지 않는다. 계좌 식별은 우리가 이미 가진 12자 해시 참조
(`account_reference`)로만 하고, 통보의 계좌번호로 다시 만들지 않는다.

## 상태 전이

주문번호(`ODER_NO`)로 내부 주문을 찾는다. 찾지 못하면 대조 불일치다.

| 조건 | 전이 |
|---|---|
| `RFUS_YN` = `1` | `REJECTED` |
| `CNTG_YN` = `2`, 누적 체결 수량 = 주문 수량 | `FILLED` |
| `CNTG_YN` = `2`, 0 < 누적 체결 수량 < 주문 수량 | `PARTIALLY_FILLED` |
| `CNTG_YN` = `1`, 거부 아님 | 전이 없음. 통보 사실만 기록 |

체결 통보(`CNTG_YN`=`2`)의 누적은 `직전 누적 + CNTG_QTY`다. 평균 체결가는 수량 가중 평균으로
다시 계산한다.

취소 확정은 이 단계에서 통보로 전이하지 않는다. 취소 확인 통보의 `RCTF_CLS`·`ACPT_YN` 조합이 실제
통보로 대조되기 전에는 취소 상태를 추측하지 않고, 취소 확정은 기존 경로(취소 응답과 마감 후 폴링)에
남긴다.

## 대조와 차단

| 상황 | 코드 | 처리 |
|---|---|---|
| 내부에 없는 주문번호 | `UNKNOWN_BROKER_ORDER` | 자동매매 `PAUSED`, 사유 `ACCOUNT_NOT_RECONCILED` |
| 누적 체결 수량이 주문 수량 초과 | `FILL_EXCEEDS_ORDER` | 같음 |
| 종결 상태 주문의 체결 수량 변경 | `TERMINAL_STATE_CHANGED` | 같음 |
| 통보 종목이 내부 주문과 다름 | `SYMBOL_MISMATCH` | 같음 |
| 통보의 주문수량이 내부 주문 수량과 다름 | `ORDER_QUANTITY_MISMATCH` | 같음. 주문번호 대조가 어긋났다는 뜻이므로 체결을 반영하지 않는다 |
| 프레임 형식·복호화·필드 수 위반 | `NOTIFICATION_UNPARSABLE` | 같음. 체결을 놓쳤을 수 있으므로 차단한다 |
| 단절 구간에 미체결 주문이 있었음 | `NOTIFICATION_GAP` | 같음 |

차단 상태에서도 수신과 기록은 계속한다. 재개는 사람이 원인을 확인한 뒤 CLI로 상태를 전이한다.

## 리스너 상태와 제출 게이트

리스너는 세션 행 하나를 유지하고 주기적으로 심박을 갱신한다.

| 항목 | 값 |
|---|---|
| 심박 주기 | 10초 |
| 부착 판정 허용 지연 | 30초 |
| 재연결 대기 | 1·2·4·8·16·30초(상한 30초) |

제출 전제조건에 다음을 추가한다. 어긋나면 증권사를 호출하지 않고 `LISTENER_NOT_ATTACHED`로 차단한다.

- 같은 환경의 리스너 세션이 `connected`이고 심박이 허용 지연 안이다.

연결이 끊어지면 세션을 `disconnected`로 바꾸고 `listener_state` 이벤트에 사유를 남긴다. 재연결
시점에 그 환경의 미체결 주문(`SUBMITTED`·`PARTIALLY_FILLED`)이 하나라도 있으면 놓친 통보가 있을 수
있으므로 `NOTIFICATION_GAP`으로 차단한다. 없으면 이벤트만 남기고 계속한다.

## 저장

리비전 `20260819_0016`이 `trading` 스키마에 다음을 추가한다.

| 대상 | 의미 |
|---|---|
| `trading.fill_notification` | 통보 한 건. append-only. 마스킹된 본문과 정규화 필드를 함께 보관한다 |
| `trading.notification_session` | 리스너 세션 하나. 연결 상태와 심박, 단절 사유를 보관한다 |
| `automation_event.event_type`에 `listener_state` 추가 | 연결·단절·재연결을 상태 전이·API 실패와 구분한다 |

`fill_notification`의 주요 컬럼은 `order_id`(내부 주문, 대조 실패 시 비어 있음), `broker_order_id`,
`notification_kind`, `symbol`, `quantity`, `price`, `broker_event_time`, `received_at`,
`account_reference`, `masked_payload`, `problem`이다. 같은 주문번호에 여러 통보가 쌓이므로 유일 제약을
두지 않고, `(broker_order_id, received_at)` 인덱스로 조회한다.

원본은 `operations.raw_api_response`에 남기지 않는다. 웹소켓 프레임은 HTTP 응답이 아니고 계좌번호를
포함하므로, 마스킹된 본문을 `fill_notification.masked_payload`에 보관하는 것이 이 경로의 원본
보존이다.

## 검증 조건

- 완료: 접속키가 발급되고 구독이 성공하며 `output.key`·`output.iv`가 수신된다.
- 완료: `PINGPONG`에 응답해 연결이 유지된다.
- 완료: 실제 체결 통보가 복호화되고 필드 순서가 이 계약의 표와 일치한다.
- 완료: 저장된 통보와 API 응답, 로그에 계좌번호·계좌명·고객ID·HTS ID·접속키가 없다.
- 완료: 리스너를 끈 상태에서 제출하면 증권사 호출 없이 `LISTENER_NOT_ATTACHED`로 차단된다.
- 완료: 미체결 주문이 있는 상태로 부착하면 `NOTIFICATION_GAP`을 기록한다. 자동매매가 정지 가능
  상태(`ARMED`·`RUNNING`)일 때만 `PAUSED`로 전이하고, 그 밖에는 기록만 남긴다.
- 대기: 우리 제출 경로로 낸 주문 1건의 부분체결 또는 전량체결이 장중에
  `FILLED`/`PARTIALLY_FILLED`로 확정된다.
- 대기: 마감 후 폴링 재대조가 통보로 만든 누적과 일치한다.

## 이 단계의 한계 (기록)

- 취소·정정 확인 통보의 전이 규칙은 실측 대조 전까지 넣지 않는다. 취소 확정은 취소 응답과 마감 후
  폴링이 담당한다.
- 통보에는 체결 건별 고유 식별자가 없다. 중복 반영 방지는 "수신 프레임을 한 번만 처리한다"는
  프로세스 성질과 append-only 저장에 기댄다. 증권사가 같은 체결을 두 번 밀어주는 사례가 관측되면
  계약을 고쳐 중복 판별 키를 정의한다.
- 리스너 부착 여부는 CLI 출력과 이벤트로만 보인다. 모의매매 콘솔 화면에 상태 표시를 추가하는 것은
  후속 작업이다.
- 실전 환경 TR(`H0STCNI0`)과 실전 웹소켓 주소는 구현하지 않는다.
- 여러 리스너를 동시에 띄우는 구성은 지원하지 않는다. 같은 환경에 세션이 둘 이상 `connected`로
  남으면 중복 반영 위험이 있으므로, 리스너는 시작 시 같은 환경의 이전 세션을 종료 처리한다.
