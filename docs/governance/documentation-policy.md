# 문서 동기화 정책

- 상태: 승인
- 승인일: 2026-08-11
- 적용 범위: 구현, 테스트, 설정, 배포 및 프로젝트 문서

## 목적

구현과 문서의 차이를 변경 시점에 발견하고, 기계가 생성할 수 있는 사실은 자동 생성하며, 정책과 설계 변경은 사람이 승인하도록 한다.

## 기본 원칙

1. 코드에서 결정되는 API, 스키마, 설정값 및 리포트는 코드로부터 생성한다.
2. 설명형 문서는 구현 및 테스트와 같은 변경 단위에서 갱신한다.
3. 승인된 정책과 구현이 충돌하면 문서를 구현에 맞춰 자동으로 덮어쓰지 않는다.
4. 주문, 리스크, 권한, AI 실행 경계 및 주요 아키텍처 변경은 ADR과 사람의 승인이 필요하다.
5. 모든 프로젝트 문서는 `docs/` 아래에 둔다. `AGENTS.md`와 `.github/pull_request_template.md`는 각각 에이전트 및 GitHub가 지정 위치에서 읽는 운영 제어 파일이므로 예외로 한다.

## 문서 유형별 처리

| 유형 | 기준 원본 | 자동화 | 승인 |
|---|---|---|---|
| OpenAPI, DB 스키마, 설정값 | 코드와 스키마 | 자동 생성 및 차이 검사 | 일반 코드 리뷰 |
| 문서 목록 | `docs/` 파일과 메타데이터 | 자동 생성 | 불필요 |
| 구현·운영 설명 | 코드, 테스트, ADR | AI 수정 제안 | 코드 리뷰 |
| UI 디자인·브라우저 QA | 디자인 토큰, 컴포넌트, 최신 캡처 | 영향 감지 및 증거 갱신 | 코드 리뷰 |
| 제품 요구사항과 ADR | 승인된 의사결정 | 영향 감지 및 초안 생성 | 사람의 명시적 승인 |
| 주문·리스크 정책 | 승인 문서와 실행 가능한 계약 | 불일치 시 병합 차단 | 필수 |

## 변경 감지 절차

1. 변경 파일을 `change-map.yaml`의 `code` 패턴과 비교한다.
2. 일치하는 규칙이 있으면 해당 규칙의 `docs` 중 하나 이상이 같은 변경에 포함되어야 한다.
3. 동작이나 계약에 영향이 없는 내부 변경은 PR 본문에 `docs-not-required: 사유`를 남길 수 있다.
4. 사유 없이 관련 문서가 누락되면 CI가 실패한다.
5. 생성 문서가 최신이 아니거나 내부 링크가 끊어져도 CI가 실패한다.

`change-map.yaml`은 별도 YAML 라이브러리 없이 초기 저장소에서도 실행할 수 있도록 JSON 호환 YAML 형식을 사용한다.

## 개발자 명령

```bash
# 생성 문서 갱신
python3 scripts/docs_guard.py generate

# 생성 문서, 링크, 매핑 무결성 검사
python3 scripts/docs_guard.py check

# 특정 변경의 문서 영향 검사
python3 scripts/docs_guard.py drift \
  --changed-file backend/src/auto_stock_trading/domain/orders/service.py \
  --changed-file docs/spec/trading-safety-policy.md
```

Git 저장소에서는 `--changed-file` 대신 `--base-ref <기준 커밋>`을 사용할 수 있다.

## AI 에이전트 작업 규칙

AI 에이전트는 구현 전에 변경 매핑을 확인하고 다음 순서로 처리한다.

1. 변경된 동작과 계약을 테스트에서 확인한다.
2. 관련된 생성 문서를 재생성한다.
3. 설명형 문서의 수정안을 코드와 같은 변경에 포함한다.
4. 승인 정책과 구현의 충돌은 자동 해소하지 않고 사용자에게 결정 근거와 함께 보고한다.
5. 최종 전달 전에 문서 검사를 실행한다.

## PR 확인 항목

- 변경된 동작을 설명하는 관련 문서가 함께 수정됐는가?
- 자동 생성 문서를 다시 생성했는가?
- 주문·리스크·AI 실행 경계 변경에 ADR과 승인이 있는가?
- 문서가 필요 없다면 구체적인 `docs-not-required` 사유가 있는가?
