# ADR-0016: 실주문 신호 원천 경계

- 상태: 승인
- 결정일: 2026-08-25
- 승인: 2026-08-25 사용자 승인. 다섯 질문 모두 초안대로 — ① 첫 원천은 규칙형 v4 하나(ML·AI 제외),
  ② 신호는 저장된 사실, ③ 후보는 보유와의 차집합만, ④ 신호 작업은 장 시작 전 별도 예약,
  ⑤ 모의 전용
- 관련 결정: [ADR-0004 AI 신호와 주문 실행 분리](0004-ai-execution-separation.md), [ADR-0015 자동 스케줄 주문 제출 경계](0015-scheduled-order-submission.md), [ADR-0007 모의투자 주문 계획과 위험검사 경계](0007-paper-order-planning-and-risk.md), [ADR-0008 모의투자 주문 제출·체결 동기화 경계](0008-paper-order-submission.md)
- 관련 정책: [거래 안전 정책](../spec/trading-safety-policy.md), [모의투자·실전투자 전환 게이트](../spec/paper-to-live-gate.md)
- 관련 계약: [백테스트 전략 계약](../data/backtest-strategy-contract.md), [주문 계획·위험검사 데이터 계약](../data/order-planning-risk-contract.md)

## 배경

ADR-0015를 승인받고 구현에 들어가 막혔다. 예약 작업이 계획을 만들려면 **무엇을 사고 팔지** 정하는
원천이 필요한데 그것이 없다.

### 지금 있는 것과 없는 것 (2026-08-24 코드 확인)

| | 상태 |
|---|---|
| 백테스트 전략 v1~v4 | 있다. 저장된 구간에 대해 회차·신호를 만든다 |
| ML 모델 레지스트리·예측 | 있다(`ml/`, `predict`) |
| 확정 일봉·수정주가 데이터셋 | 있다 |
| **저장된 실주문 신호** | **없다.** `strategy` 스키마에는 백테스트 실행 기록만 있다 |
| **신호 → 주문 후보 변환** | **없다.** `SignalCandidate`를 만드는 곳은 사람의 CLI와 기존 주문 두 곳뿐이다 |

`OrderPlanner`는 후보를 **입력으로 받는다.** 요청의 전략 이름·버전·파라미터는 계보 기록용이며 신호를
만들지 않는다. 2026-08-19 실주문도 사람이 종목과 방향을 지정해 나갔다.

### 이것은 ADR-0004의 완화가 아니라 이행이다

ADR-0004는 이미 사슬을 정해 두었다.

```text
AI 분석·예측 → 전략 신호 → 목표 포지션 → 결정적 위험검사 → 주문 계획 → 증권사 API
```

그 문서의 결정 중 하나가 "**전략 엔진이 AI 신호를 목표 포지션 후보로 변환한다**"다. 지금 없는 것이
바로 그 변환 계층이며, 이 ADR은 경계를 넓히는 것이 아니라 비어 있던 칸을 채운다. ADR-0004의 금지
사항(AI에 주문 자격증명 제공, AI 출력을 주문 API에 직접 전달)은 그대로 유지된다.

## 측정한 사실이 설계를 정한다

### 1. 확정 봉은 전날까지만 있다 — 그래서 백테스트의 인과 모델과 자연히 맞는다

일봉 확정은 거래일 **15:40 KST 이후 두 번 일치 관측**을 요구한다(`_DAILY_BAR_FINALITY_CUTOFF`).
따라서 주문 허용시간(09:05~15:15) 안에서 계산하는 신호는 **T-1 종가까지의 확정 봉**만 쓸 수 있다.

백테스트는 "T 종가 신호 → 다음 거래일 시가 체결"로 실행한다(계약 v1). 실주문에서 T-1 확정 봉으로
신호를 만들고 T에 주문하면 **같은 인과 구조**가 된다. 미래 정보를 쓰지 않으려고 규칙을 새로 만들
필요가 없다 — 확정 봉만 쓰는 것이 곧 그 규칙이다.

### 2. 체결 시점은 백테스트와 다르다 — 숨기지 않고 기록해야 한다

백테스트는 다음 거래일 **시가**에 체결한다. 실주문은 예약 작업이 도는 시각의 **현재가** 기준으로
계획한다(ADR-0015: 15분 주기, 09:05~15:15). 첫 슬롯(09:05)이 시가에 가장 가깝지만 같지 않다.

이 차이는 전략 성과와 실주문 성과가 갈리는 구조적 이유이며, 없애려면 시가 주문(현재 금지된 시장가 계열)
이 필요하다. 없애는 대신 **차이를 기록**한다.

### 3. 위험검사는 이미 후보를 받는다

`SignalCandidate(symbol, side)`만 만들면 그 뒤는 전부 있다 — 목표 수량 산정(종목 상한 NAV 10%를
≤5% 주문으로 분할), 정책 §3·§4 전수 검사, `client_order_id` 중복 방지. 이 ADR이 만드는 것은
**후보 목록 하나**이며 주문 크기나 한도를 새로 정하지 않는다.

## 결정

### 1. 첫 신호 원천은 규칙형 v4(ETF 자산배분) 하나로 한정한다

ML 모델과 AI 분석은 이 슬라이스에서 신호 원천으로 쓰지 않는다. 근거:

- ADR-0004는 "AI를 완전히 비활성화해도 규칙형 전략과 주문 시스템은 동작해야 한다"고 정했다. 첫 연결을
  규칙형으로 하면 그 성질이 구조적으로 성립한다.
- v4는 대상이 **승인된 6종 ETF**이고 유니버스 자체에 정책 §1(레버리지·인버스 금지)이 박혀 있다.
  v2·v3는 200종목을 대상으로 하므로 첫 연결의 노출 면적이 훨씬 크다.
- v4는 월말 리밸런싱이라 **하루에 신호가 바뀌는 날이 한 달에 한 번**이다. 실측에서 41회 리밸런싱 중
  실제 체결은 56건이었다. 관측 가능한 빈도다.
- v1(단일 종목 MA-RSI)은 종목을 사람이 정해야 하므로 지금과 다르지 않다.

### 2. 신호는 계산 즉시 **저장된 사실**이 된다 — 계획이 그 사실을 읽는다

신호를 계획 시점에 즉석 계산하지 않는다. `strategy.live_signal`에 신호를 append-only로 남기고
계획 경로가 그것을 읽어 후보로 쓴다.

- 감사가 성립한다: 어떤 확정 봉 버전으로 어떤 점수가 나와 어떤 후보가 됐는지가 주문과 별개 사실로 남는다.
- 같은 신호로 두 번 계획해도 후보가 같다(계획 재실행이 신호를 흔들지 않는다).
- 신호와 주문 사이에 **사람이 볼 수 있는 창**이 생긴다.

신호 행에는 최소한 전략 이름·버전, canonical 파라미터, 기준 거래일(T-1), 사용한 봉 버전 해시, 목표
종목과 방향, 점수를 남긴다. 백테스트 실행 기록과 같은 계보 원칙이다.

### 3. 신호는 백테스트와 **같은 코드**로 만든다

`etf_allocation_rebalances`를 그대로 호출한다. 실주문용으로 규칙을 다시 구현하지 않는다. 지표·서열·대피
규칙이 두 곳에 있으면 백테스트로 검증한 전략과 실제로 주문하는 전략이 갈라진다.

입력은 **확정 봉만**이며 기준일은 T-1이다(측정 1). 확정 봉이 부족해 회차를 만들 수 없으면 신호를
만들지 않는다 — 값을 만들지 않는다.

### 4. 목표 포지션 → 후보 변환은 보유와의 차집합이다

신호의 목표 종목과 계좌의 현재 보유를 비교해 후보를 만든다.

- 목표에 있고 보유에 없으면 **매수** 후보.
- 보유에 있고 목표에 없으면 **매도** 후보.
- 둘 다 있으면 후보를 만들지 않는다. **비중 조정(트리밍)은 하지 않는다** — 백테스트 엔진의 트리밍은
  백테스트 안의 규칙이고, 실주문에서 비중을 맞추려면 부분 매도 판단이 필요하다. 그것은 별도 결정이다.

### 5. 신호 생성은 장 시작 전에, 주문과 분리된 작업으로 돈다

신호 계산은 확정 봉만 쓰므로 장 시작 전에 끝낼 수 있다. 예약을 두 단계로 나눈다.

- **신호 작업**: 08:30 KST 전후, 확정 봉으로 신호를 만들어 저장한다. 증권사 주문 자격증명이 필요 없다.
- **주문 작업**: ADR-0015의 계획-제출 체인이 저장된 신호를 읽어 후보로 쓴다.

ADR-0015 결정 1(계획-제출 체인)은 유지된다 — 체인이 읽는 것이 사람의 CLI 인자에서 저장된 신호로
바뀔 뿐이다. 기준가는 여전히 계획 시점에 새로 조회한다(10초 규칙).

### 6. 하루 한 번 사람이 켜는 성질은 그대로다

신호가 저장돼 있어도 자동매매가 `RUNNING`이 아니면 주문은 나가지 않는다(정책 §6, ADR-0015 결정 3).
신호 작업이 자동매매 상태를 올리는 경로는 만들지 않는다.

### 7. 백테스트와의 체결 시점 차이를 신호 행에 기록한다

측정 2의 차이를 사실로 남긴다. 신호는 "T-1 종가 기준"이고 주문은 "T 장중 현재가 기준"이므로, 신호 행에
기준 거래일과 기준 종가를 남기고 주문 행에는 이미 기준가·수신시각이 남는다. 두 값의 차이가 곧
백테스트-실주문 괴리의 관측값이 된다.

### 8. 모의 전용이다

실전 환경에서는 신호 원천을 활성화하지 않는다. 실전 연결은 전환 게이트를 통과한 뒤 **별도 승인**이다.

## 결과

승인되면:

- ADR-0015의 선행 조건이 해소되고 자동 스케줄 제출을 구현할 수 있다.
- 백테스트로 검증한 전략이 같은 코드로 실주문 후보를 만든다.
- 신호가 주문과 별개 사실로 남아 "왜 이 주문이 나갔는가"를 신호까지 되짚을 수 있다.
- **사람이 종목을 고르지 않는 첫 경로**가 된다. 이것이 이 결정의 실질적 비용이며, 결정 1(규칙형 하나)·
  4(트리밍 없음)·6(하루 한 번 사람이 켠다)·8(모의 전용)이 그 범위를 제한한다.

승인되지 않으면:

- 실주문 후보는 계속 사람이 지정한다. 자동 스케줄 제출(ADR-0015)은 구현되지 않은 상태로 남는다.

## 대안

- **ML 모델을 첫 신호 원천으로**: 8단계 산출물을 바로 쓴다. 그러나 모델 실패가 첫 자동 주문 경로에
  직결되고, ADR-0004가 요구한 "AI 없이도 동작"을 검증하기 전에 AI에 의존하게 된다.
- **v2·v3(200종목)을 첫 원천으로**: 유니버스가 넓어 전략 가치는 크지만 첫 연결의 노출 면적이 크고,
  200종목 일봉 백필이 선행돼야 한다.
- **신호를 저장하지 않고 계획 시점에 계산**: 테이블이 늘지 않는다. 그러나 감사가 주문 행에만 남고,
  계획 재실행이 신호를 다시 계산해 결과가 흔들릴 수 있으며, 사람이 볼 창이 없다.
- **목표 비중까지 실주문에서 맞춘다(트리밍 포함)**: 백테스트와 더 가까워진다. 그러나 부분 매도 판단이
  필요하고 회전율·비용이 늘며, 결정 4를 넘는 별도 결정이다.

## 구현 (2026-08-25)

| 결정 | 구현 |
|---|---|
| 1. v4 하나 | `LiveSignalGenerator`가 `etf_allocation_rebalances`만 호출한다 |
| 2. 저장된 사실 | `strategy.live_signal`·`live_signal_target`(리비전 `20260825_0029`), 기준일당 하나이며 덮어쓰지 않는다 |
| 3. 같은 코드 | 백테스트 전략 함수를 그대로 호출한다. 실주문용 재구현 없음 |
| 4. 차집합 | `domain/strategies/live_signal.py`의 순수 함수 |
| 5. 별도 예약 | `worker/execution/signals.py --generate` / `--status` (증권사 자격증명 불필요) |
| 6. 하루 한 번 사람이 켠다 | 신호 CLI는 자동매매 상태를 바꾸지 않는다 |
| 7. 괴리 기록 | 신호 행에 `basis_date`·`basis_close_json` |
| 8. 모의 전용 | `KisEnvironment.PAPER` 확인 |

계획 연결은 `worker/execution/planning.py --from-signal`이다. 저장된 신호와 **방금 조회한 보유**의
차집합으로 후보를 만든다 — 저장된 스냅샷에서 보유를 읽으면 그 사이 체결이 반영되지 않아 이미 보유한
종목을 다시 살 수 있다. 계획 기록의 전략 신원은 **신호가 가진 신원**을 그대로 옮긴다(계보가 갈라지면
안 된다).

### 구현 중 드러난 규칙 하나

백테스트의 `rebalance_dates`는 **창의 마지막 거래일도 회차로 본다**(장부를 닫아야 하므로). 실주문에서
T-1까지의 창에 그 규칙을 쓰면 **매일이 회차**가 되어 월말 전략이 일간 전략으로 바뀐다. 그래서
`completed_rebalance_dates`(다음 거래일이 다른 달인 날만)를 따로 두고 테스트로 고정했다.

### 실측 (2026-08-25)

- 신호 생성: 기준일 **2026-08-24**(T-1), 회차 **2026-07-31**(마지막 완결 월말), 목표
  `069500`(점수 1.525)·`133690`(0.260). 재실행은 `exists`로 덮어쓰지 않았다.
- 계획 연결: 목표 2종 − 보유 `005930` → **후보 3개**(매수 2·매도 1), 결과는
  `blocked block_code=AUTOMATION_NOT_RUNNING`. **신호가 저장돼 있어도 사람이 켜지 않으면 주문이
  나가지 않는다**(결정 6)는 것이 실측으로 확인됐다.

## 재검토 조건

- 규칙형 연결이 한 달 이상 관측되면 ML 신호 원천을 별도 결정으로 검토한다.
- 200종목 일봉 백필이 끝나면 v2·v3 연결을 검토한다.
- 백테스트-실주문 괴리(결정 7의 관측값)가 전략 판단을 바꿀 정도면 체결 시점 규칙을 다시 정한다.
- 실전 전환 게이트를 통과하면 결정 8을 다시 검토한다.
