# ADR-0017: 마감 후 재대조와 세션 종료 주문 처리 경계

- 상태: 승인 (2026-08-25 구현)
- 결정일: 2026-08-25
- 승인: 2026-08-25 사용자 승인. 질문 1을 **조건부 종결**로 확정했다(집계 일치를 미체결 확인의 근거로
  인정하고, 어긋나거나 집계가 없으면 사람 확인을 요구한다). 질문 2·3·4는 초안의 입장대로 확정했다 —
  새 상태 `expired`를 추가하고(`canceled` 재사용은 사실과 다르다), 게이트 강화를 지금 넣고, 기존 잔재
  `0000009931`은 이 규칙으로 소급하지 않고 ADR-0010의 `--attest`로 별도 정리한다

## 배경

ADR-0009는 결정 1에서 "웹소켓 통보를 장중 확정 경로로 쓰고 **마감 후 일별주문체결조회로 재대조**"를
승인했다. 같은 문서의 실측 후속이 그 후반부를 이미 무효화했다.

> 일별주문체결조회가 **모의환경에서는 시각·파라미터와 무관하게 주문별 행(`output1`)을 주지 않는다**는
> 사실이 나왔다(9가지 조합). … 결정 문구는 승인 상태로 두고, **대체 재대조 수단은 사용자 결정으로
> 남긴다.**

이 문서가 그 유보된 결정을 해소한다. **문서와 구현의 충돌을 고치는 것이 아니다** — 승인된 문서가
스스로 남겨둔 빈칸을 채우는 것이다.

빈칸이 비어 있는 동안 실제 잔재가 생겼다. 2026-08-25에 접수된 주문 `0000009931`(005930 1주)이
미체결로 남았고, 마감 후 `--sync`는 `updated=0 problems=0`으로 끝났다. 그 주문은 지금도
`submitted`이며 **이후 어떤 자동 검사에도 걸리지 않는다.**

## 측정한 사실 (2026-08-25)

### 1. `output1`은 마감 후에도 비어 있다 — 세 번째 확인

15:41 KST 실행에서 증권사 응답은 다음과 같았다. 그날 실제로 2주가 체결됐다.

```
rt_cd=0  msg_cd=70070000  msg1="모의투자 조회할 내역(자료)이 없습니다."  output1=0건
```

2026-08-19 15:42(9가지 조합)와 오늘을 합쳐 독립 측정 3회다. 이 TR로 **주문별** 체결을 확인하는 경로는
모의환경에 존재하지 않는다. 재시도·파라미터 조정으로 해결하려 하지 않는다.

### 2. 그러나 `output2`는 계좌 단위 집계를 준다 — 그리고 우리 값과 일치했다

같은 응답의 `output2`는 비어 있지 않았다.

```json
{"tot_ord_qty": "2", "tot_ccld_qty": "2", "tot_ccld_amt": "498000",
 "prsm_tlex_smtl": "70", "pchs_avg_pric": "249000.0000"}
```

우리 내부 당일 체결은 `0000009999` 2주 × 249,000원 = 498,000원이다. **수량·금액·평균가가 정확히
일치한다.** 즉 주문별 귀속은 불가능하지만 **합계 수준 재대조는 가능하다.** ADR-0009가 찾던 대체 수단이
같은 응답 안에 있었고, 우리가 `output1`만 보고 있었다.

### 3. `tot_ord_qty`는 미체결 주문을 세지 않는다

당일 접수 수량은 3주(2주 + 1주)이고 취소된 018880 주문이 254주 더 있는데 `tot_ord_qty=2`다.
`tot_ccld_qty`와 같은 값이므로 이 집계는 **체결분만** 센다. 따라서 집계로는 미체결 주문의 존재를 알 수
없고, **집계가 일치한다는 것은 "우리가 미체결로 아는 주문이 실제로도 체결되지 않았다"는 증거**가 된다.
이 방향의 추론만 유효하다. 반대로 미체결 주문이 몇 건 살아 있는지는 이 응답으로 알 수 없다.

### 4. 세션 종료 시 열린 주문은 이후 어떤 검사에도 걸리지 않는다

`open_orders`는 `plan.trading_date == 인자로 받은 날짜`로 한정된다(`trading_order_writes.py`의
`tracked_orders_query`). 결과로 세 가지가 모두 비껴간다.

- 다음 거래일 리스너 부착 시 `NOTIFICATION_GAP`이 뜨지 않는다(당일 열린 주문이 없으므로).
- 다음 거래일 `PendingExposure`에 들어가지 않는다.
- 게이트의 `UNRECONCILED_ITEMS`는 `reconcile_problem` **이벤트**를 세므로 0으로 남는다.

즉 잔재는 조용히 축적된다. 이것이 이 문서가 필요한 실제 이유다.

### 5. `--sync`는 빈 응답을 `problems=0`으로 보고한다

`rt_cd=0`이므로 호출은 성공이고, 대조할 행이 없으므로 전이도 문제도 만들지 않는다. 출력만 보면
"이상 없음"으로 읽힌다. **조회 성공과 대조 수행은 다른 사건인데 같은 신호로 표시된다.**

## 결정

### 1. 마감 후 재대조는 계좌 단위 집계로 한다 — 주문별 귀속을 만들지 않는다

`output2`의 `tot_ccld_qty`·`tot_ccld_amt`를 우리 내부 당일 체결 합계와 대조한다. 주문별 귀속은
원천이 없으므로 **추정하지 않는다.** 합계가 맞는데 어느 주문의 것인지 배분하는 계산은 만들지 않는다 —
그 배분은 사실이 아니라 우리가 만든 값이 된다.

장중 확정은 그대로 실시간 통보가 담당한다(ADR-0009 결정 1 전반부는 유효하다). 이 재대조는 **검증자**이며
확정 경로가 아니다.

### 2. 집계 불일치는 자동으로 고치지 않고 자동매매를 정지한다

불일치는 `reconcile_problem` 자동매매 이벤트(사유 `ACCOUNT_NOT_RECONCILED`)로 남기고 `paused`로
전이한다. 우리 값을 증권사 집계에 맞춰 조정하는 코드는 만들지 않는다 — 어느 주문이 틀렸는지 모르는
상태에서 합계를 맞추면 틀린 사실이 사실처럼 저장된다. ADR-0010의 사람 확인 경로로 해소한다.

### 3. 조회 성공과 대조 수행을 구분해 보고한다

`--sync` 결과에 대조 가능 여부를 분리해 표시한다(`reconciled=matched|mismatched|unavailable`). `output2`까지 비어
있으면 `problems=0`이 아니라 **대조 불가**로 보고한다. 성공처럼 보이는 무작동을 없앤다.

### 4. 세션 종료 시 열린 주문은 집계가 일치할 때만 종결한다

정규장 종료 후 미체결 주문이 체결될 수는 없지만, **우리가 관측하지 않은 사실을 단정하지 않는다.**
그래서 조건을 붙인다.

- 당일 집계 재대조가 **일치**하면, 남은 열린 주문은 체결되지 않았음이 집계로 확인된 것이므로 종결
  상태로 옮긴다. 사유 코드는 `SESSION_ENDED`이며 근거로 집계 값을 함께 남긴다.
- 집계가 **불일치**하거나 `output2`조차 없으면 **종결하지 않는다.** 열린 채로 두고
  `reconcile_problem`으로 남겨 사람 확인(ADR-0010)을 요구한다.

종결 상태는 기존 `canceled`를 재사용하지 않는다. 우리가 취소한 것이 아니므로 그렇게 적으면 사실이
아니다. 새 종결 상태 `expired`를 추가한다(마이그레이션 필요, `OrderState`·CHECK 제약·화면 라벨 동반).

이 처리는 **자동 스케줄이 아니라 마감 후 `--sync` 실행 안에서** 일어난다. 사람이 없는 동안 주문 상태가
바뀌는 새 경로를 만들지 않는다(ADR-0015 결정 1과 같은 이유).

### 5. 열린 주문 검사는 거래일 경계를 넘는다

`open_orders`에 "해당 환경의 모든 미종결 주문"을 읽는 조회를 더한다. 리스너 부착 검사와 게이트 판정은
이 조회를 쓴다. 당일 한정 조회는 `PendingExposure` 계산(당일 한도 계산)에만 남긴다 — 그쪽은 당일이
맞다.

### 6. 게이트의 미조정 판정에 열린 잔재를 포함한다

`UNRECONCILED_ITEMS`는 현재 `reconcile_problem` 이벤트만 센다. **거래일이 지난 미종결 주문 수**를
더한다. 실전 전환 조건이 "미조정 0건"인데 잔재가 안 세어지면 조건이 거짓으로 통과한다.

### 7. 모의 전용이다

실전 환경에서는 `output1`이 정상 동작할 가능성이 있고(모의 한정 제약일 수 있다), 그때는 주문별 재대조가
가능해진다. 이 결정은 모의환경 한정이며, 실전 전환 시 실측으로 재검토한다(§재검토 조건).

## 결과

- 마감 후 재대조가 처음으로 실제 수행된다. 지금은 매일 무작동이었다.
- 세션 종료 잔재가 자동으로 정리되거나, 정리되지 않을 때는 사람에게 보인다. 조용히 남는 경로가 없어진다.
- 게이트의 미조정 조건이 실제 잔재를 반영한다. 실전 전환 판정이 이 방향으로는 느슨해지지 않는다.
- 비용: 새 종결 상태 하나(마이그레이션), 조회 하나, `--sync` 출력 형식 변경. 화면은 라벨 추가만
  필요하다(이벤트 타입 추가 시 라벨 누락으로 사유 코드가 노출된 전례가 있다 — 인계 문서 134번).

## 대안

### A. 주문별 재대조를 다른 TR로 찾는다

정정취소가능주문조회(`VTTC8036R`)는 모의환경 미지원으로 이미 측정됐다(`msg_cd=90000000`). 다른 후보를
계속 찾는 것은 세 번 측정된 제약에 네 번째 시도를 더하는 것이다. 채택하지 않되, 실전 전환 시에는 다시
확인한다.

### B. 세션 종료 시 무조건 자동 만료

간단하지만 관측 없이 종결한다. 증권사가 실제로 그 주문을 취소했는지 우리는 모른다. 이 시스템의 원칙과
어긋나므로 채택하지 않는다.

### C. 항상 사람 확인을 요구한다

가장 보수적이지만 매 거래일 사람 작업이 늘어난다. 집계가 일치하는 정상적인 날에도 사람을 부르면 확인이
형식이 되고, 진짜 불일치를 알리는 신호가 묻힌다. 결정 4의 조건부가 이 절충이다.

### D. 아무것도 하지 않는다

현 상태다. 잔재가 조용히 축적되고 게이트가 거짓으로 통과할 수 있다. 채택하지 않는다.

## 승인이 필요한 질문 (모두 답을 받았다 — 2026-08-25)

1. **결정 4의 조건부 종결을 받아들이는가?** → **조건부 종결로 확정.** 집계 일치를 "미체결 확인"의
   근거로 인정한다. 대안 C(항상 사람 확인)는 채택하지 않았다 — 정상적인 날에도 사람을 부르면 확인이
   형식이 되고 진짜 불일치 신호가 묻힌다.
2. **새 상태 `expired`를 추가하는가?** → **추가한다.** `canceled` 재사용은 우리가 취소하지 않은 것을
   취소했다고 적는 것이므로 사실과 다르다.
3. **결정 6의 게이트 강화를 지금 넣는가?** → **넣는다.** 실전 전환 조건이 이 방향으로 엄격해지는 것은
   의도한 결과다. 잔재가 안 세어지면 "미조정 0건" 조건이 거짓으로 통과한다.
4. **잔재 `0000009931`을 이 규칙으로 소급 처리하는가?** → **소급하지 않는다.** ADR-0010의 `--attest`로
   별도 정리한다. 규칙 도입 전의 건을 새 규칙으로 처리하면 규칙의 첫 실행이 검증 없이 과거 데이터에
   적용된다.

   **이 답은 실행할 수 없다(2026-08-25 실측).** `--attest`는 `refused reason=LISTENER_COVERED`로
   거부한다. ADR-0010은 **리스너가 존재하기 전에 제출된 주문만** 사람이 확인해 종결하도록 제한하며
   (`submitted_at < earliest_session_start`), 그 주문은 리스너 커버 구간에서 제출됐다. 통보는 이 주문에
   대해 아무것도 오지 않았으므로 양쪽이 모두 막힌다 — 커버됐으니 attest 불가, 통보가 없었으니 전이
   없음. 초안을 쓸 때 이 제약을 확인하지 않았다. 남은 실행 가능한 경로는 이 문서의 자동 종결(다음
   `--sync`)뿐이며, 그것은 질문 4의 답을 되돌리는 선택이므로 사람의 결정 사항으로 남긴다.

## 미측정

- 모의환경에서 정규장 종료 후 미체결 주문이 증권사 쪽에서 실제로 어떻게 처리되는지(자동 취소·익일
  이월 여부). 관측 수단이 없어 결정 4는 이 사실에 의존하지 않도록 설계했다.
- `output2`가 취소·정정이 섞인 날에도 체결분만 세는지. 오늘 표본은 취소 2건·정정 1건을 포함했고
  `tot_ord_qty=tot_ccld_qty=2`였으나 한 번의 관측이다.
- 부분 체결이 있는 날의 `tot_ccld_amt` 반올림 처리.

## 재검토 조건

- 실전 전환 시 `output1`이 주문별 행을 주는지 재측정한다. 주면 결정 1을 주문별 재대조로 강화한다.
- `output2`가 체결분만 센다는 관측이 다른 날 표본에서 깨지면 결정 1·4의 근거가 바뀐다.
- 실시간 통보 경로가 하루 이상 붙지 못한 날이 생기면, 그날의 집계 재대조는 확정 경로의 대체가 아니라
  **불일치 탐지**만 한다는 점을 다시 확인해야 한다.

## 구현 (2026-08-25)

승인 당일 구현했다. 결정 1~7 전부.

- 순수 판정: `domain/orders/session_close.py` — `compare_daily_totals`(수량·금액 모두 같을 때만 일치),
  `close_session_orders`(일치일 때만 `expired`, 아니면 문제만 남긴다), `session_ended`(서울 15:30 기준).
  **장 종료를 15:15가 아니라 15:30으로 잡았다** — 종가 단일가(15:20~15:30)까지 체결될 수 있다.
- 원천: `KisDailyFillsResponse.output2`를 `BrokerDailyTotals`로 정규화한다. 없으면 `None`이며 0과
  구분한다(픽스처 `daily_fills_no_totals.json`이 이 경우를 고정한다).
- 문제 코드는 둘로 나눴다: `DAILY_TOTALS_MISMATCH`(증권사가 다르게 안다)와
  `DAILY_TOTALS_UNAVAILABLE`(대조할 근거가 없다). 결정 2가 이름한 `ACCOUNT_NOT_RECONCILED`는 자동매매
  정지 사유로 그대로 쓴다 — 문제 기록과 정지 사유는 다른 층이다.
- 새 상태: 리비전 `20260825_0031`이 `order`와 `order_event` 두 CHECK 제약에 `expired`를 더한다.
  이벤트 쪽을 빼면 전이는 되는데 그 사실을 남길 수 없다. 상태 그래프는 `submitted`·`partially_filled`
  에서만 `expired`로 간다.
- 종결 쓰기는 `apply_fill`이 아니라 `trading_session_writes.expire_order`다. 사유 코드가
  `SESSION_ENDED`이고 근거로 당일 집계를 `detail`에 남긴다. 체결 동기화와 같은 사유를 쓰면 감사
  기록에서 "증권사가 체결을 알려줬다"와 "장이 끝나 더 체결될 수 없다"가 구분되지 않는다.
  `trading_store.py`가 이미 검토 한계를 넘어 새 모듈로 분리했다.
- 보고: `--sync` 출력에 `reconciled=matched|mismatched|unavailable`과 `expired=<건수>`가 붙는다.
- 게이트: `GateMeasurements.stale_open_orders`(거래일이 지난 미종결 주문)를 `UNRECONCILED_ITEMS`에
  더한다. 판정 시각의 서울 거래일을 라우터가 넘긴다.
- 화면: 주문 상태 라벨에 `expired = 기간만료`를 더했다. 라벨이 없으면 사용자에게 코드가 그대로
  노출된다(인계 문서 134번의 전례).

`detail`은 외부 알림 본문에 들어가지 않는다(본문은 사유 코드만 쓴다). 알림에는
`submitted → expired · SESSION_ENDED`로 나간다.

### 실데이터 검증 (2026-08-25 17:4x KST, 읽기 전용)

종결은 일부러 돌리지 않았다 — 승인 질문 4가 잔재 `0000009931`을 이 규칙으로 소급하지 않기로 했고,
`--sync`를 그대로 실행하면 집계가 일치해 자동 종결됐을 것이다. 그래서 집계 대조만 확인했다.

```
broker   = BrokerDailyTotals(filled_quantity=2, filled_amount=Decimal('498000'))
internal = InternalDailyTotals(filled_quantity=2, filled_amount=Decimal('498000.00000000'))
verdict  = matched
rows     = 0
```

`rows=0`이 이 결정의 전제를 다시 확인한다 — 주문별 행은 여전히 없고 집계만 온다. 스케일이 다른
Decimal 비교(`498000.00000000 == 498000`)는 수치 비교라 일치한다.

### 종결 경로 실데이터 검증 (2026-08-25 21:36 KST)

`--attest`가 거부되면서 질문 4의 답이 실행 불가로 확인됐고, 사용자가 **자동 종결에 맡기는 쪽으로
답을 바꿨다**. 그 결정으로 이 경로의 첫 실데이터 실행이 이뤄졌다.

```
updated=0 problems=0 paused=False reconciled=matched expired=1 states=- reasons=-
```

주문 `0000009931`의 감사 기록:

```
1  ->planned
2  planned->submitted        40600000
3  submitted->submitted      cancel_requested   EMERGENCY_STOP
4  submitted->expired        SESSION_ENDED      당일 체결 합계 수량 2 금액 498000.00000000
```

시퀀스 3이 이 잔재가 생긴 이유를 설명한다 — **비상정지가 취소를 요청했지만 확인 통보가 오지 않았다.**
그래서 상태 선택이 옳았음이 확인된다: 취소를 요청했을 뿐 증권사가 취소했다는 사실은 관측하지 못했고,
`expired`는 "더 체결될 수 없다"만 주장한다. `canceled`로 적었다면 관측하지 않은 사실을 적는 것이었다.

종결 후 미종결 주문은 0건이고, 게이트의 잔재 기여분도 0이 됐다.

### 드러난 후속 과제 (결정 필요)

게이트의 `UNRECONCILED_ITEMS`는 `reconcile_problem` 이벤트를 **해소 여부 없이 전부** 센다. 잔재
기여분이 0이 된 뒤에도 누적 이벤트 27건 때문에 조건은 여전히 미충족이며, **한 번이라도 문제가 생기면
이 조건은 다시 충족될 수 없다.** 실전 전환 조건으로는 "미해소 0건"이어야 한다. 승인된 게이트 의미를
바꾸는 일이므로 이 문서에서 고치지 않고 기록만 남긴다.

**미검증**: 집계 불일치의 실데이터 관측(일부러 만들 수 없다).
