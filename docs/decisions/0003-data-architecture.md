# ADR-0003: PostgreSQL 중심 데이터 아키텍처 채택

- 상태: 승인
- 결정일: 2026-08-11

## 배경

프로젝트는 주문과 포지션 같은 트랜잭션 데이터, OHLCV와 수급 같은 시계열 데이터, 재무·공시 데이터, 백테스트·모델 메타데이터를 함께 관리해야 한다. 초기에는 일봉 중심이며 단일 서버에서 운영한다.

## 결정

- PostgreSQL 18을 운영 데이터의 단일 영속 원본으로 사용한다.
- 주문, 포지션, 위험 결정, 데이터 동기화 상태를 PostgreSQL 트랜잭션으로 관리한다.
- 시계열 데이터는 일반 테이블로 시작하고 규모가 확인된 뒤 네이티브 파티셔닝을 적용한다.
- 대규모 연구·학습 데이터는 버전이 지정된 Parquet 스냅샷으로 생성한다.
- Parquet 처리는 Polars, 연구용 SQL은 DuckDB를 사용한다.
- Valkey는 작업 큐와 단기 캐시에만 사용하고 영속 원본으로 사용하지 않는다.
- **저장은 원문을 보존하고, 파생·복원은 조회 계층에서만 한다.** 원천이 표기를 바꿔도(계정 접두 개정, 표준 계정 미태깅) 저장된 사실을 고쳐 쓰지 않는다. 조회가 산술로 값을 복원할 때는 응답이 그 방식을 명시해 원문에서 직접 읽은 값과 구별되게 한다(2026-08-23 추가, [재무 지표 정의 계약](../data/financial-indicator-contract.md) §표준계정 결측 시 복원 규칙이 첫 적용 사례).
- **관측하지 않은 사실을 상태로 적지 않는다.** 종결 상태는 그 종결이 어떻게 확인됐는지에 따라 나눈다 — 우리가 취소해 종결된 주문(`canceled`)과 장이 끝나 더 체결될 수 없음이 증권사 집계로 확인된 주문(`expired`)은 다른 사실이므로 같은 값에 담지 않는다. 상태를 합치면 감사 기록에서 두 사건을 구분할 수 없고, 근거가 없는 종결과 근거가 있는 종결도 같아진다(2026-08-25 추가, [ADR-0017](0017-post-close-reconciliation-and-session-end.md)이 첫 적용 사례).

## 대안

### TimescaleDB 선행 도입

현재 데이터 규모와 조회 패턴이 확인되지 않았고 확장 의존성이 늘어나므로 보류한다.

### 데이터 레이크 선행 도입

객체 스토리지, 카탈로그와 동기화 운영 비용이 초기 규모에 비해 크므로 보류한다.

### SQLite

동시 작업, 장기 worker와 주문 트랜잭션을 안정적으로 지원하기 부족하므로 채택하지 않는다.

## 결과

- 주문과 시장 데이터의 일관성을 한 DB에서 관리할 수 있다.
- 백업과 복구 절차가 단순하다.
- 분석 부하는 Parquet 스냅샷으로 운영 DB와 분리할 수 있다.
- 틱 데이터 규모가 커질 경우 후속 저장소 확장이 필요할 수 있다.

## 재검토 조건

- 네이티브 파티셔닝 후에도 시계열 조회와 적재 성능이 기준을 충족하지 못한다.
- 틱 데이터의 장기 보관이 핵심 요구사항이 된다.
- 데이터셋 크기가 단일 서버의 저장·처리 한도를 넘는다.
